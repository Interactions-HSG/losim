## Two layers

<Columns cols={2}>
  <Card title="Your system" icon="code">
    Ordinary Java, ordinary `.proto` files, ordinary generated stubs. Real
    transport, real marshalling, real allocation, real threads.
  </Card>
  <Card title="losim" icon="layer-group">
    gRPC interceptors that slow calls or drop them, a machine model that caps
    memory and disk, and a scale engine that shrinks the world and projects the
    result back.
  </Card>
</Columns>

Your program does not import a simulator type into a signature. It calls peers over
`io.grpc.Channel` and gets back the messages your schema declared. Delete losim
from the classpath and the code still compiles. What a call costs, what a machine
is, and what goes wrong are declared in the scenario.

That separation is why the numbers mean something. When losim says a machine ran
out of memory, the machine really was made small, your code really filled it, and
the failure happened in your code for the same reason it would happen at full size.

<Note>
Nothing is downloaded and nothing is generated at build time. The toolchain is
vendored into the repository, so the same commands produce the same result on a
laptop, in the devcontainer, and in a Codespace.
</Note>

## The workflow

<Steps>
  <Step title="Write a schema">
    A `.proto` with your services and messages. gRPC is the only way machines talk.
  </Step>
  <Step title="Write services and a job">
    Handlers are plain methods you can call from a plain unit test. The job is one
    class with a `run(Cluster)` method that drives the cluster.
  </Step>
  <Step title="Write a scenario">
    A YAML file: how many machines, what they are, what they serve, where they are,
    and what goes wrong at 400 reference milliseconds.
  </Step>
  <Step title="Run it and look">
    One command produces one trace. The trace is the interchange format, and the
    bill, the viewer, and your own assertions all read it.
  </Step>
</Steps>

## More than a toy

<AccordionGroup>
  <Accordion title="Machines are really small, so running out of memory is real" icon="memory">
    A machine's memory cap is enforced against a retained-heap walk, which measures
    what the machine is still holding, not what it allocated. Those are different
    numbers, and only one of them decides an out-of-memory.

    [How a machine is modelled ->](/engine/a-machine)
  </Accordion>
  <Accordion title="Concurrency is real, so queueing is real" icon="microchip">
    Each machine gets one thread pool sized to its vCPU count. Four concurrent calls
    into a two-vCPU machine queue, and the wait shows up in the trace as its own
    event.

    [Concurrency inside a machine ->](/write/concurrency)
  </Accordion>
  <Accordion title="A projection carries its confidence, or it is absent" icon="chart-line">
    In scaled mode the engine fits a law per resource and then checks whether it
    bends. When it cannot support the result, the field is empty with a reason
    rather than filled with a plausible number.

    [When the engine refuses ->](/run/when-it-refuses)
  </Accordion>
  <Accordion title="Numbers that stopped meaning what they say are marked" icon="triangle-exclamation">
    Reading the real clock, writing a real file, opening your own channel, and
    sharing a static field between machines do not throw. Each produces a run full
    of plausible figures, every one of them wrong in a direction nobody can see.

    [Trust markers ->](/engine/trust)
  </Accordion>
</AccordionGroup>
