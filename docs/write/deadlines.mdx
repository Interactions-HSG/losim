```java
var stub = ThumbnailerGrpc.newBlockingStub(channel)
        .withDeadlineAfter(2_000, TimeUnit.MILLISECONDS);   // 2000 refMs
```

You write milliseconds because that is gRPC's API. losim interprets them as
**reference** milliseconds and converts the remaining time by `k_time` before
passing it to gRPC.

<Note>
Without conversion, an 800 refMs deadline at 40x would fire too early. The client
interceptor performs the conversion before gRPC applies the deadline.
</Note>

## Deadline check

Latency is slept when the response comes back. A call that succeeded on the callee
but whose round trip outlasted the deadline is turned into a failure:

```
DEADLINE_EXCEEDED: the network outlasted the deadline
```

The check prevents a call from succeeding after its network delay exceeded the
deadline. `crossZone: 30 refMs` and `withDeadlineAfter(50, MILLISECONDS)` therefore
use the configured reference-time values.

## Caller errors and trace events

The caller gets `StatusRuntimeException` with `DEADLINE_EXCEEDED`, and the trace
gets an `rpc_timeout` event carrying `why`:

```json
{ "kind": "rpc_timeout", "vm": "master",
  "detail": { "to": "w1", "method": "lab.Thumbnailer.Thumbnail",
              "call": 41, "status": "DEADLINE_EXCEEDED", "why": "unreachable" } }
```

<Warning>
**The callee is not told.** A frozen node can keep the call on its threads; a dead
node never received it. A handler may still run, hold memory, or occupy a core after
the caller gives up.
</Warning>

## A call with no deadline

losim waits **five seconds** and then gives up on your behalf, so a simulation without
an explicit deadline still terminates.

Five seconds of reference time can exceed a short run's horizon. If a run takes much
longer than expected and ends with many timeouts, check the stub's deadline first.

## Choosing a deadline

A deadline should exceed the expected callee duration under load:

```java
Thumbnail: { fixed: 3 refMs, perUnit: 240000 refNs }   # 25 frames -> 3 + 6 = 9 refMs
```

This is nine reference milliseconds of work on a two-vCPU node. If four calls arrive
at once and the node has two cores, the fourth waits for earlier calls, so observed
duration is closer to 27 refMs plus the round trip.

<Tip>
Deadlines that are too tight can make a healthy system appear broken. Set the first
deadline generously, inspect `handler` spans under load, then tighten it above the
observed duration.
</Tip>

## Deadlines and retries interact

The retry policy sits **outside** the recording interceptor, so each attempt is a
fresh call with the *same* `CallOptions` and absolute deadline. A growing backoff can
exhaust the deadline before all attempts run.

```json
{ "kind": "retry", "detail": { "attempt": 1, "of": 3, "after": "DEADLINE_EXCEEDED",
                               "backoffRefMs": 50.0 } }
{ "kind": "retry_done", "detail": { "attempts": 2, "status": "DEADLINE_EXCEEDED" } }
```

## Observe a deadline

The same call, run twice, against a deadline that is and is not enough:

```yaml patience.yaml
seed: 3
nodes:
  master:
    instance: m5.large
    zone: eu-central-1a
    runs: { losim.Job: src/lab/RenderJob.java }
  workers:
    count: 2
    prefix: w
    instance: c5.large
    zone: [eu-central-1a, eu-central-1b]
    runs: { Thumbnailer: src/lab/Shrinker.java }
    overrides:
      w1:
        failures:
          - { freeze: true, at: 500 refMs, for: 900 refMs }

network:
  sameZone:  1 refMs
  crossZone: 40 refMs           # enough that a zone hop matters
```

```java RunExperiments.java
Experiments.here()
        .run("patience.yaml")
        .show();
```

The frozen node remains visible but answers nothing. With a generous deadline the
caller waits 900 refMs; with a shorter deadline, `rpc_timeout` markers appear when
it expires.
