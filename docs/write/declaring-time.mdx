takes:
  Shrinker:

**In the scenario, not in the handler.** A duration is a claim about the machine a
design would run on, which is the scenario's subject — and it leaves your Java with
no losim symbol in it at all.

## Time is declared, not measured

losim shrinks the workload **and** the machines by the same factor, so memory and
bytes survive it honestly: a machine that would exhaust 16 GiB at full scale
exhausts 16 MiB here, in your own code, for the same reason.

Time does not survive it, because **the host's CPU is not shrunk**. It runs at full
speed on a five-thousandth of the data, so every handler is genuinely instant.
Without a declared duration there is no queueing, no contention, no deadline
pressure and no critical path — which is most of what a cluster is interesting for.

Measuring instead does not work at this scale either. Handler durations at probe
size sit inside the host's own jitter, where the fitted time exponent moves by 0.25
between seed sets of an *identical* workload. A number that moves that much when
nothing changed is not a measurement.

<Note>
So it is declared, and it is **optional**. An rpc nobody prices takes no time —
deliberately, rather than a made-up amount. A handler nobody has timed should run
at whatever speed it runs, not at a speed somebody guessed.
</Note>

## Reference time

`refMs` is time on a **reference machine**: two vCPUs, running alone. That is the
unit, and it is the unit precisely so that the declaration composes with everything
else. The server interceptor sleeps:

```
refMs × machineFactor ÷ k_time
```

| | |
|---|---|
| `machineFactor` | `2 ÷ vcpu`, from the instance catalogue. A 2-vCPU machine takes 1×; a 4-vCPU machine takes 0.5×; a degraded machine multiplies on top. |
| `k_time` | the run's global compression. |

A declaration of `refMs = 3` therefore means *three milliseconds of work on a
two-core machine*, which is a claim about your code that stays true whatever cluster
it lands on and however compressed the run is.

## The two terms

<ParamField path="refMs" type="double" default="0">
  What one call takes **regardless of what is in it** — the fixed part. Known
  before the handler runs, and slept **before** it, on the machine's own pool
  thread. Marshalling, setup, a lookup: the cost of being called at all.
</ParamField>

<ParamField path="refNsPerUnit" type="double" default="0">
  What each unit of input adds, in reference **nanoseconds**. Nothing outside the
  handler can know how much input there was, so the handler declares it with
  `Losim.current().units(n)` and this part is slept **after the body returns**,
  before the response leaves.

  Slept before the response leaves rather than after, because a caller waits for
  work that has not finished — and by that point the handler has said how much
  there was.
</ParamField>

<Warning>
A handler that never calls `units(n)` is charged the **fixed part only**, and its
span says so. If your per-unit term looks like it is doing nothing, that is
almost always why.
</Warning>

## Choosing numbers

There is no right answer, and that is the point — the declaration is a claim about
your design that you are making explicitly rather than discovering by accident.
Some anchors:

| | roughly |
|---|---|
| a hash lookup, a field copy | far below 0.01 refMs — do not annotate it |
| parsing or validating a message | 0.1 – 1 refMs |
| an image operation, a compression, a sort of a few thousand items | 1 – 20 refMs |
| something you would put on a dashboard | 50 refMs and up |

<Tip>
Two designs are compared by comparing scenarios, so what matters is that your
declarations are **consistent between the designs you are comparing**. A handler
declared at 3 refMs in one design and 30 in the other is not a comparison of
designs.
</Tip>

## There is a floor, and no knob above it

The clock cannot express a duration finer than about **0.05 ms** of real time — the
measurement's own overhead dominates below that. losim handles it by *owing* the
cost rather than losing it, and the ledger is good for about fifty times below the
floor. Past that, the engine says so:

```
this run is clocked at 40x real time, and lab.Thumbnailer.Capacity costs 0.0004
refMs — 6x below what the sleep debt can still settle at that compression, so its
timings would drift rather than be owed. Give that cost site more to do, or lower
the scale: at scale 1 the clock runs at 20x.
```

Notice what the remedy is not. `k_time` is the engine's, derived from
[the scale](/ref/scale); there is no number to turn down. What is wrong is a cost
site too small to be timed, and that was true of the design before losim said it.

## Where the numbers go

Under the class `runs:` names, and then the rpc — not under the rpc alone:

```yaml
machines:
  workers: { count: 4, prefix: w, instance: c5.large, zone: eu-central-1a, runs: [Shrinker] }

takes:
  Shrinker:
    Thumbnail: { refMs: 3, refNsPerUnit: 240000 }
```

A duration belongs to the **code**, not to the operation. Two implementations of
one rpc, on two machines, is how one design is compared with another — and a table
keyed on the rpc would say they take the same time.

Written under a class nothing places, or an rpc that class does not serve, it is
refused before anything runs, with the line it was written on. That is what stands
in for the annotation's one advantage: an annotation followed a renamed method, and
a table cannot, so the scenario stops loading instead of quietly costing nothing.
