## Memory measures

| | |
|---|---|
| **`allocMb`** | what your program allocated, from `getThreadAllocatedBytes` on this node's own pool threads. losim's allocation on those threads is subtracted. |
| **`memoryMb`** | the **most it was ever seen holding**, measured by a retained-heap walk from the node's own service instances. |

An accumulating and a streaming design can allocate similar totals. The cap checks
retained memory, which distinguishes them.

```
accumulating service: allocated 21.9 MB, retains 20.6 MB
streaming service:    allocated 15.6 MB, retains  0.0 MB
```

## Running out

When a walk finds a node holding more than its cap:

```json
{ "kind": "oom", "vm": "w2", "detail": {
    "resource": "memory", "capMb": 4.0, "demandMb": 11.83,
    "objects": 148_221, "cause": "retained heap exceeded the node" } }
```

The node is killed, and callers detect the failure when calls to it reach their
deadlines.

<Note>
The check runs on the sampler's cadence **and** once at the end of the run. A node
that exceeds its cap after the last sample is still checked by the final walk.
</Note>

## The boundary of a node

The walk starts from the node's service instances and their fields. It counts data
owned by that node and stops at shared runtime infrastructure:

<Columns cols={2}>
  <Card title="Counted" icon="check">
    The walk counts your fields, collections, and protobuf messages held by the node.
  </Card>
  <Card title="Not counted" icon="xmark">
    The walk excludes other nodes, shared runtime infrastructure, telemetry, spans,
    the clock, the network, servers, channels, executors, and threads.
  </Card>
</Columns>

If a node needs to hold data that does not hang off a service:

```java
Losim.current();                      // …no. There is no API for this from a handler.
```

it must be reachable from a service instance. A static cache is shared across nodes
and is [flagged](/engine/trust).

## Triggering a memory limit

Memory caps come from the instance type, and a simulation can override one node:

```yaml
nodes:
  workers:
    count: 4
    prefix: w
    instance: c5.large              # 4096 MB
    runs: { Thumbnailer: src/lab/Shrinker.java }
    overrides:
      w2: { memoryMb: 4 }           # cannot hold its share, and will say so
```

This tests behavior when one node is smaller than its peers and whether the system
detects the failure.

<Tip>
Above `scale: 1` you do not write caps. The engine solves them per node and resource
so demand relative to capacity is preserved. [How caps are solved ->](/engine/solving-caps)
</Tip>

## Series by tick

Per node, per tick:

| channel | |
|---|---|
| `retainMb` | what it is holding now |
| `memCapMb` | its cap |
| `memPct` | the first over the second |
| `allocMb` | what your program has allocated so far, cumulative |

The heap walk costs about 0.06 µs per object, so a busy node is walked every eighth
tick rather than every tick. `retainMb` changes at that sampling cadence.

<Note>
**`allocMb` only ever rises.** The meter reads the node's own threads, including
losim bookkeeping; the series subtracts that bookkeeping.

The underlying counter is not monotonic when sampled from another thread. A buffer
swap can make the observed value fall by up to a TLAB's size. The series therefore
reports a high-water mark rather than a decreasing allocation counter.

A thread reading its own counter cannot be mid-swap while it asks, so measurements
inside a handler are not affected by this issue.

A killed node can no longer be metered. losim reports a `meter_lost` event and keeps
the last readable value instead of reporting zero.
</Note>

## Memory practices

<AccordionGroup>
  <Accordion title="Release the input after processing" icon="lightbulb">
    A handler that keeps the request while building the response retains both. Build
    the response separately and release the request when possible.
  </Accordion>
  <Accordion title="Compare streaming and accumulating" icon="water">
    Run two services with the same work and cap, one retaining answers and one
    streaming them. Compare `memoryMb` in the `nodes` channel.
  </Accordion>
  <Accordion title="reveal the variable, not just the size" icon="eye">
    `reveal("distinctItems", index.size())` tells the scale engine what memory is
    *really* a function of. Peak memory on an accumulating node often depends on
    distinct items rather than processed units. Fitting against the wrong variable
    makes the exponent sensitive to input changes. [Writing to
    scale ->](/write/scale-writing)
  </Accordion>
</AccordionGroup>

## Observe a memory limit

One node deliberately too small for what it is asked to hold:

```yaml filling-up.yaml
seed: 1
scale: 2

nodes:
  coordinator:
    instance: m5.large
    zone: eu-central-1a
    runs: { losim.Job: src/lab/AccumulateJob.java }
  workers:
    count: 3
    prefix: w
    instance: c5.large
    zone: eu-central-1a
    runs: { Accumulator: src/lab/Accumulator.java }
    overrides:
      w2: { memoryMb: 8 }        # cannot hold its share, and will say so

input:
  unit:  row
  count: 60000
```

```java RunExperiments.java
Experiments.here()
        .run("filling-up.yaml")
        .show();
```

`w2` has the same display size as its peers but reaches its cap first. Press `]` to
jump to the `oom` marker and inspect the node.
