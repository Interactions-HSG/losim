The system is ordinary gRPC and can run without the simulator. When something is
wrong, identify the layer first and isolate the other layers.

<Warning>
**Start with isolated tests before running a simulation.**

A run uses real threads and a real wall clock. Pausing one pool thread does not pause
other nodes, the clock, the sampler, or the fault dispatcher. Debugging timings are
therefore not representative.

Use a running simulation at [level 4](#level-4-inside-a-run), after the isolated
tests.
</Warning>

## Level 1: Handler alone

No simulator or transport is involved. A breakpoint behaves as it does in any
ordinary Java test.

```java
@Test void oneFrameBecomesOneThumbnail() {
    var shrinker = new Shrinker();                       // breakpoint here
    Thumbs thumbs = shrinker.thumbnail(oneBatch());      // step into this
    assertEquals(1, thumbs.getThumbsCount());
}
```

Step into `thumbnail`: it is your code called directly on the test thread.

| diagnostic target | |
|---|---|
| wrong arithmetic, wrong loop bounds, an off-by-one in the output | almost everything, in practice |
| a builder you forgot to `build()` | yes |
| a message field you never set, so it silently defaults | yes |
| anything about how nodes behave together | **no** |

<Note>
`Losim.current()` still resolves here and does nothing: recording calls are silent,
state calls throw. So a handler that reveals and records is testable as it stands.
[Handler testing ->](/write/handler-testing)
</Note>

## Level 2: Two handlers

Still no gRPC. If handler A calls handler B, test the pair by calling the methods
directly:

```java
@Test void aForwardedBatchComesBackWhole() {
    var big   = new Shrinker();
    var small = new Shrinker();

    // Call the method directly instead of using a channel.
    Thumbs thumbs = small.thumbnail(batchOf(40));
    assertEquals(40, thumbs.getThumbsCount());
}
```

This tests request construction and response handling without transport.

## Level 3: Real gRPC without the simulator

<div id="level-3" />

When the issue may be on the wire, such as marshalling, status, or `oneof` handling,
run a real gRPC server in the test. grpc-java's in-process transport is vendored:

```java test/WireTest.java
import io.grpc.*;
import io.grpc.inprocess.*;
import lab.pb.*;
import org.junit.jupiter.api.*;

class WireTest {

    private Server server;
    private ManagedChannel channel;
    private ThumbnailerGrpc.ThumbnailerBlockingStub stub;

    @BeforeEach void start() throws Exception {
        String name = InProcessServerBuilder.generateName();

        // directExecutor: the handler runs on the CALLING thread, so a breakpoint
        // inside it stops everything, and the stack you land in goes all the way
        // back to the test. This keeps the call stack in the test process.
        server = InProcessServerBuilder.forName(name)
                .directExecutor()
                .addService(new Shrinker())
                .build()
                .start();

        channel = InProcessChannelBuilder.forName(name).directExecutor().build();
        stub = ThumbnailerGrpc.newBlockingStub(channel);
    }

    @AfterEach void stop() {
        channel.shutdownNow();
        server.shutdownNow();
    }

    @Test void aBatchSurvivesTheWire() {
        Thumbs thumbs = stub.thumbnail(batchOf(3));      // ← step into the handler
        assertEquals(3, thumbs.getThumbsCount());
    }

    @Test void aFailureCarriesItsReason() {
        var e = assertThrows(StatusRuntimeException.class,
                () -> stub.thumbnail(Batch.getDefaultInstance()));
        assertEquals(Status.Code.INTERNAL, e.getStatus().getCode());
        assertTrue(e.getStatus().getDescription().contains("empty"));  // your adapter's message
    }
}
```

This level checks transport behavior directly:

  - that your adapter turns an exception into a status with a description instead
    of a bare `UNKNOWN`;
- that a `oneof` or a `map` field round-trips the way you expect;
- that a `NO_SIDE_EFFECTS` annotation actually landed on the descriptor:
  ```java
  assertTrue(ThumbnailerGrpc.getThumbnailMethod().isIdempotent()
          || ThumbnailerGrpc.getThumbnailMethod().isSafe());
  ```
      which is what losim's [retry gate](/write/retries) checks later and is easier
      to diagnose here than as a simulation refusal.

<Warning>
**`ManagedChannelBuilder`, `InProcessServerBuilder`, and `directExecutor()` are all
things the verifier flags** in a *system*. Here they are valid because this test has
no simulation.

Keep this code in a **test source set that no service or job references.** The
verifier walks outward from the classes your simulation names; a test nothing points
at is never reached. If you put a harness like this in a class your service imports,
it will be walked, and it will be flagged — rightly, because then it could run
inside a real system.
</Warning>

### Limits at this level

| diagnostic target | behavior |
|---|---|
| a simulation's `simulatedDuration:` | does not apply. There is no simulation and no interceptor, so no duration is slept. |
| `k_time` | is absent. Time uses the host clock. |
| memory and disk caps | not enforced. Nothing is walking the heap. |
| `peers()`, `channelTo()`, `here()` | throw because there is no system. |
| byte counts, spans, failures | not recorded. |

Do not draw performance conclusions from level 3. It tests behavior and transport.

## Level 4: Inside a run

<div id="level-4-inside-a-run" />

Use level 4 when the bug depends on interactions between nodes. Read the trace
channels in this order:

<Steps>
  <Step title="Shrink the system and stop compressing time">
    ```yaml
    nodes:
      master:
        instance: m5.large
        zone: eu-central-1a
        runs: { losim.Job: src/lab/RenderJob.java }
      w0:
        instance: m5.large
        zone: eu-central-1a
        runs: { Thumbnailer: src/lab/Shrinker.java }
                             # no failures are configured
    ```
    Start with one master, one worker, and no failures. If it fails here, the
    additional system features are not the cause.
  </Step>

  <Step title="Read the span tree first">
    Every server span is opened **under** the call that reached it, so the tree is a
    distributed call stack.

    The fastest way to read it is the [Spans view](/viewer/views#spans):

    ```java RunExperiments.java
    Experiments.here().run("mine.yaml").show();   // then: view=spans
    ```


    Each bar is segmented into **out / queue / working / back**, separating waiting
    from handler time. The view also shows self time, the critical path, and stragglers.

    Or print it, which needs nothing but python:

    ```python
    import json, collections
    t = json.load(open("build/mine.json"))
    kids = collections.defaultdict(list)
    for s in t["spans"]: kids[s["parent"]].append(s)

    def show(pid, depth=0):
        for s in sorted(kids[pid], key=lambda s: s["t0"]):
            print(f'{"  "*depth}{s["vm"]:<12} {s["kind"]:<8} {s["label"]:<34} '
                  f'{s["t0"]:8.1f} -> {s["t1"]:8.1f}  {s["status"]}')
            show(s["id"], depth + 1)
    show(0)
    ```

    A call attached to the **root** instead of its caller usually means the parent
    header was lost, often because the channel was built outside losim.
  </Step>

  <Step title="Turn payloads on and read what actually crossed">
    `--telemetry FULL` records each call's real argument and result. If a handler
    produced the wrong answer, inspect its span's `detail.arg`.
  </Step>

  <Step title="Ask losim for its own stack">
    ```bash
    LOSIM_DEBUG=1 java -cp "$CP" losim.cli.Main simulate mine.yaml --cp build/losim/classes
    ```

    Exit code 3 means something went wrong **inside losim**; this prints its stack.
    Exit code 2 is a simulation configuration error.
  </Step>

  <Step title="Use a breakpoint last">
    If you must: use **one worker**, no failures, and no deadline on the call being
    stopped. Treat the resulting trace as control-flow evidence, not measurement.
  </Step>
</Steps>

## Symptoms

<AccordionGroup>
  <Accordion title="Every call times out, and nothing looks wrong">
    Check for a deadline that is too tight for the declared cost plus queueing.
    Then check `queue_wait` — a two-vCPU node given eight concurrent calls takes
    four waves, and the fourth wave's caller may have given up before its turn.
  </Accordion>
  <Accordion title="The run takes ten times as long as it should, and ends in timeouts">
    A stub with **no deadline** waits five reference seconds before losim gives up
    on your behalf. Set deadlines.
  </Accordion>
  <Accordion title="One node does all the work; the others show zero calls">
    Check service discovery. You may be passing the Java class name to
    `peersServing`, where it wants the **service name from the `.proto`** — or you
    fetched the peer list once and are indexing it with something that is always
    zero.
  </Accordion>
  <Accordion title="Handlers never overlap: the span tree is a staircase">
    A blocking stub inside the dispatch loop. Use `newFutureStub`, dispatch
    everything, then collect. [Calling peers ->](/write/calling-peers)
  </Accordion>
  <Accordion title="`Losim.current()` throws inside a handler">
    ```
    this thread has no node: work started on a thread the node did not create…
    ```
    Something is running your work on a thread the node did not create — a raw
    `Thread`, an `Executors` pool, `CompletableFuture.supplyAsync`, or a
    `parallelStream`. [Concurrency ->](/write/concurrency)
  </Accordion>
  <Accordion title="It works, but the numbers are implausibly good">
    Read the trust block at the end of the run. A channel built by hand costs no
    bytes and survives partitions; a real file bypasses the disk cap; a static field
    shared between nodes makes every per-node figure meaningless.
    [Trust markers ->](/engine/trust)
  </Accordion>
  <Accordion title="The simulation is refused and nothing runs">
    Exit code 2, with the file and line. That is the loader, and the message names
    exactly what is wrong. [Messages ->](/ref/messages)
  </Accordion>
</AccordionGroup>
