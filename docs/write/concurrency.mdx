Each node has one thread pool sized to its **vCPU count** from the instance
catalogue. Four calls into a two-vCPU node queue.

```
a1.medium   1 vCPU        m5.large   2 vCPU
c5.large    2 vCPU        m5.xlarge  4 vCPU
c5.xlarge   4 vCPU        m5.2xlarge 8 vCPU
c5.4xlarge 16 vCPU        r5.large   2 vCPU
```

The pool uses platform threads and the wall clock. Multiple invocations of one
handler can run concurrently.

## Queueing

```json
{ "kind": "queue_wait", "vm": "w3", "detail": { "ms": 18.4 } }
```

The event is recorded when a call waits more than a microsecond for a core. It
separates queueing from handler execution time.

The series carries both halves per node:

| | |
|---|---|
| `inflight` | handlers **using** a core right now |
| `queued` | handlers **waiting** for one |
| `busyPct` | `inflight ÷ vcpu`, capped at 100 |

At `busyPct: 100` with growing `queued`, the node is receiving more work than its
pool can serve. A node at `busyPct: 0` while work remains may be missing from
placement.

## Thread ownership

<Warning>
**Work must run on the node's own threads.**

Every pool thread belongs to one node, which defines the attribution boundary for
`getThreadAllocatedBytes`. Application-created threads are outside that boundary.

```java
new Thread(() -> heavyWork()).start();                    // flagged
Executors.newFixedThreadPool(4).submit(this::heavyWork);  // flagged
CompletableFuture.supplyAsync(this::heavyWork);           // flagged — common pool
list.parallelStream().map(this::heavyWork).toList();      // flagged — common pool
Thread.ofVirtual().start(() -> heavyWork());              // flagged
```

These calls do not necessarily throw. They produce measurements that omit work, so
the verifier reports the file and line.
</Warning>

A handler that reaches for `Losim.current()` from such a thread gets told directly:

```
this thread has no node: work started on a thread the node did not create
loses its identity, and its memory and CPU are attributed to nobody.
Wrap the node's executor with Context.currentContextExecutor.
```

## Ways to add concurrency

<Columns cols={2}>
  <Card title="Serve more calls at once" icon="arrows-split-up-and-left">
    A node's pool serves several calls simultaneously. Smaller splits and more
    concurrent calls let the pool use its available cores.
  </Card>
  <Card title="Call more nodes" icon="server">
    Spread work by **calling peers**, not by starting application threads.
  </Card>
</Columns>

<Note>
Raw threads are **not banned**. The verifier flags work outside the node pool because
it cannot attribute that work to a node. Calling peers is usually the portable way to
distribute work.
</Note>

## Shared handler state

Two calls into the same service instance can run on separate threads and access the
same fields. A non-thread-safe `HashMap` can therefore be corrupted.

```java
public final class Shrinker extends ThumbnailerBase {
    private final Map<String, Thumb> cache = new ConcurrentHashMap<>();   // yes
    private final Map<String, Thumb> broken = new HashMap<>();            // a real bug
}
```

<Tip>
To reproduce contention, use `c5.4xlarge` (16 vCPUs), dispatch enough calls to keep
the pool busy, and use a plain `HashMap`.
</Tip>

## Making contention happen

```yaml
nodes:
  small:
    instance: c5.large       # 2 vCPU
    runs: { Thumbnailer: src/lab/Shrinker.java }
```

Dispatch eight 100 refMs calls at it; they complete in roughly four waves. This is a
useful first check when timings appear too low.

## Observe queueing

Save this as `queueing.yaml`. One two-vCPU node, eight concurrent calls at 100 refMs:

```yaml queueing.yaml
seed: 1
nodes:
  master:
    instance: m5.large
    zone: eu-central-1a
    runs: { losim.Job: src/lab/FanOutJob.java }   # 8 calls with newFutureStub, then collects
  small:       { instance: c5.large, zone: eu-central-1a, runs: { Slow: src/lab/Slow.java } }
```

```java RunExperiments.java
Experiments.here()
        .run("queueing.yaml")
        .show();
```

The run should show four waves, `queue_wait` events, and `inflight` at 2 while
`queued` grows. Repeat with `c5.4xlarge` and compare the runs
[on one clock](/viewer/views#two-runs-on-one-clock).
