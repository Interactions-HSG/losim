```yaml
mode: scaled
workload:
  records: 40000000
  probe: [1000, 2000, 4000, 8000]
  fleets: [2, 4]
```

There are exactly **two** modes and no third. Direct mode runs what it declares and
every number on screen is what happened. Scaled mode always uses the engine — a
scenario cannot hand-declare a shrink factor and bypass it, because that would be a
third mode whose numbers nobody could account for.

## Running it

The same command. losim notices the mode:

```bash
java -Xmx3g -cp "${CP}build/losim.jar:build/classes" \
     losim.cli.Main run thumbs-scaled.yaml \
     --cp build/classes --out build/scaled.json
```

The first run is slow, and here is where the time goes:

```
thumbs-scaled.yaml  seed 5  scaled 8,000 -> 40,000,000 records (x5,000), k_time 20
                                              [plan fitted from 30 probe runs in 41.2s]
```

Thirty small runs — four data sizes at six seeds each, two fleet shapes, and a
fault column — climbed before the real run happens at all. Then:

```
                                              [plan cached]
```

<Note>
**The plan cache** lives in `build/.losim-plans/` and is keyed on the scenario, the
code it profiles, **and the telemetry level**. Change any of those and it refits;
change nothing and a grid of thirty runs is paid for once.

Keyed on the telemetry level because the whole claim of the accounting is that the
fitted law does not depend on how much you instrumented — and a cache that ignored
the level would make that claim untestable.

```bash
rm -rf build/.losim-plans      # force a refit
```
</Note>

## Reading the output

```
  memoryMb   = 0.0597 + 0.00187 * revealed.distinctItems^1.013  (R2 1.0000, wobble 0.000)
  wireMb     = 0.0    + 0.000151 * records^0.952                (R2 1.0000, wobble 0.004)
  diskMb       REFUSED: the ladder bends — over the lower half it grows as records^0.59
               and over the upper half as records^0.87 …
  makespan     REFUSED: its exponent moves by 0.66 between independent seed sets …

                     observed              projected
  memoryMb              6.823                34.07 k  +-x1.10
  wireMb                0.460                 2.63 k  +-x1.04
```

<AccordionGroup>
  <Accordion title="The law line" icon="function" defaultOpen>
    `resource = fixed + coefficient × variable ^ beta`

    The **fixed** term is overhead that is real at every scale — a JVM's baseline
    heap does not shrink because the workload did. The **variable** term is what
    grows.

    `R2` is how well the line went through the points it was given. `wobble` is how
    far the exponent moves when the whole thing is fitted again on independent
    seeds — and the second is the number that decides whether the law is kept.
  </Accordion>
  <Accordion title="The variable" icon="magnifying-glass">
    `revealed.distinctItems` means your own `reveal("distinctItems", …)` was chosen
    as the independent variable, over `records`. That is the engine finding what the
    resource is *actually* a function of. Peak memory is a function of how much you
    hold, not of how much went past.

    A variable that is not `records` is itself fitted against records, so the
    projection composes two well-behaved laws instead of one fragile one.
  </Accordion>
  <Accordion title="The error bar" icon="plus-minus">
    `+-x1.10` means the projection could plausibly be 10% either way. It is
    `scaleFactor ^ wobble`: an uncertainty in the exponent becomes a factor in the
    answer, and the further the projection reaches the more it matters.

    Past **x2.0** the projection no longer distinguishes anything a reader would
    have wanted distinguished, and the engine refuses it rather than printing it.
  </Accordion>
  <Accordion title="The refusals" icon="ban">
    Two different tests, answering two different questions.

    **The ladder bends** — the resource behaves differently small than large, so no
    extrapolation across means anything. Note that the refusal quotes the R², which
    is still 0.88, precisely because R² is the number a reader would reach for and
    it would not have caught this.

    **The exponent is not reproducible** — refit on independent seed sets, it lands
    somewhere else. A law whose exponent cannot be reproduced to better than its own
    effect size is a number with a line through it.

    [In full →](/engine/refusals)
  </Accordion>
</AccordionGroup>

## Two bills

```bash
java -cp "$CP" losim.cli.Main bill build/scaled.json
```

A scaled run is billed twice — for what happened, and for the job it is a model of.
The second is where it gets interesting, because a bill is quantities times prices
and the engine will not project every quantity:

```
  capacity    the fleet, for the period            -           CHF   refused
      its exponent moves by 0.793 between independent seed sets of the same
      workload, which over a factor of 6 is an error bar of x4.1
```

Capacity depends on the timeline, the timeline is the noisiest thing losim
measures, and capacity is usually the largest line. So the honest account routinely
says: the bytes cost this much, the storage costs this much, and nobody can tell you
what the machines cost.

## When there is no feasible size

```
thumbs-scaled.yaml  scaled mode: no feasible size
  memoryMb at 8000 records is only 2.4x its own fixed overhead (0.31 against 0.13);
  below 10x the fit is describing the overhead rather than the workload
  Nothing was run and nothing is projected, which is the point:
  a projection that could not be made must be absent, not guessed.
```

Feasibility is checked in both directions — large enough that the variable part
dominates the fixed overhead, small enough that the whole scaled fleet fits in the
host's heap. [What to do about it →](/run/when-it-refuses)
