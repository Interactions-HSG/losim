```yaml
network:
  sameZone:  0.4 refMs
  crossZone: 3 refMs
  jitter:    0.5 refMs
  loss:      0.01
```

All four fields are optional. The default network has no latency, jitter, or loss.

<ParamField path="sameZone" type="duration" default="0 refMs">
  One-way latency between nodes in the same zone. losim charges the **round trip**,
  so the configured value is doubled.
</ParamField>

<ParamField path="crossZone" type="duration" default="0 refMs">
  One-way latency between nodes in different zones. It is typically five to ten
  times `sameZone`, so zone placement affects call duration.
</ParamField>

<ParamField path="jitter" type="duration" default="0 refMs">
  A uniform spread on either side of the mean, drawn from the seed. A round trip
  with `crossZone: 3 refMs` and `jitter: 0.5 refMs` falls in `[5, 7]` refMs.
</ParamField>

<ParamField path="loss" type="double, 0 to 1" default="0">
  The probability that a message is **never delivered**. Values outside `[0, 1]` are
  refused: *"loss is a probability, from 0 to 1."*
</ParamField>

## Latency

The whole round trip is slept **once**, in `onClose`, on the thread that delivers the
response. For a blocking call this is the caller's thread; for a future it is the
channel executor. The callee's pool thread and measured handler duration are not
affected.

<Note>
The approximation is that the handler starts one network leg early because outbound
delay is folded into the return. Modeling the outbound leg separately would occupy
a core, add a thread per call, or block an asynchronous caller.
</Note>

## Deadline checks

```
DEADLINE_EXCEEDED: the network outlasted the deadline
```

The check prevents a call from succeeding after the network delay has exceeded its
deadline. Therefore `crossZone: 30 refMs` and
`withDeadlineAfter(50, MILLISECONDS)` use the configured network time.

## Loss, partitions, and dead nodes

```java
catch (StatusRuntimeException e) {
    e.getStatus().getCode();   // DEADLINE_EXCEEDED, always
}
```

Nothing answers before the deadline. The caller receives `DEADLINE_EXCEEDED` for a
slow peer, a dead node, a partition, or a lost packet, so application code sees the
same outcome in each case.

The trace records the cause in `why`:

| `why` | what it was |
|---|---|
| `unreachable` | the node is dead |
| `partitioned` | the link between these two is cut |
| `lost` | the draw against `loss` came up |

## Byte accounting

losim marshals each message explicitly. gRPC's in-process transport passes objects
by reference, so the transport cannot provide a byte count. The counted size is the
serialized message plus **five bytes** of gRPC framing per message.

Cross-zone bytes are counted separately, **in both directions**. Counting only the
request would omit most of a response such as a one-megabyte fetch.

<Note>
**Both directions are charged to the node that made the call**, not to the one that
answered. A node whose only cross-zone traffic is other people's requests therefore
shows `crossZoneMb: 0`.

This assigns egress to the design that chose the cross-zone call. Changing placement
changes the charge; changing which node holds the data does not.
</Note>


## Partitions

A partition applies to a pair of nodes, so configure it in one node's
[`failures:`](/ref/failures) list:

```yaml
nodes:
  w1:
    instance: c5.large
    runs: { Thumbnailer: src/lab/Shrinker.java }
    failures:
      - { partition: master, at: 900 refMs }
      - { heal: master, at: 2500 refMs }
```

The node containing the block is one end; `partition:` names the other. It is the
only failure that names another node because reachability is a pair property.

The partition cuts **both directions** between that pair only. `w1` remains alive,
appears in discovery, and serves nodes that can still reach it.
