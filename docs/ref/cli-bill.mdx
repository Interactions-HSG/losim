title: "dissaly bill"
description: "Reports observed and projected costs in four buckets."
icon: "receipt"
---

```bash
java -cp build/dissaly.jar dissaly.cli.Main bill <trace.json> [--prices <file>] [--json]
```

<ParamField path="--prices <file>" type="path" default="prices/eu-central-1.yaml">
  A price list. If the file is missing, dissaly uses its built-in defaults and reports
  that on **stderr**, keeping `--json` valid on stdout.
</ParamField>

<ParamField path="--json" type="flag">
  The four buckets as data, plus the **rates** used to compute them.

  ```json
  {
    "trace": "build/results/mine.json",
    "rates": {
      "currency": "CHF", "spotDiscount": 0.7, "egressPerGb": 0.01,
      "storagePerGbMonth": 0.1, "billingMinimumSeconds": 60,
      "buildPerServiceMonth": 250.0, "slaSeconds": 10.0,
      "latePenaltyPerSecond": 0.5, "incidentPerRerun": 0.02,
      "incidentPerLostMachine": 0.2
    },
    "observed":  { "lines": [ … ] },
    "projected": { "lines": [ … ] }
  }
  ```

  `projected` is present only for a scaled run. Notes go to **stderr**, so the
  document on stdout is clean and pipeable.

  The `rates` object lets other tools display the bill without rebuilding its pricing
  rules. The viewer's [Ledger](/viewer/views#the-ledger) uses the lines and rates
  produced here, so its closing total matches this command.
</ParamField>

<Note>
**The viewer looks for a bill by convention.** A run writes

`<name>.bill.json` beside each `<name>.json`; the page loads it when present. A trace
dragged onto the page may have no bill, in which case the viewer shows no invented
cost. [Opening a trace ->](/viewer/opening-a-trace)
</Note>

Billing is a **pure function of the trace**, so a different price list needs no
re-run.

## Cost buckets

| bucket | what it is a model of |
|---|---|
| `capacity` | the system, for the period. An idle node costs exactly as much as a busy one. |
| `consumption` | what the work burned: egress at the distance it went, and storage |
| `incidents` | zero until something breaks, then large |
| `build` | engineering time to construct and carry this design, per distinct service |

<Note>
They are printed **apart rather than summed** because each bucket informs a
different decision. Replication can increase capacity and build cost while
reducing incidents.

A line appears only when there is a quantity to report. A refused bucket is not
treated as zero cost.
</Note>

## Output lines

Each row identifies the quantity that produced it.

| bucket | line | unit |
|---|---|---|
| `build` | `services carried` | services |
| `capacity` | `<node> (<instance>)`, or `(<instance>, spot)` | node-hours |
| `capacity` | `the system, for the period` — **projected side only** | node-hours |
| `consumption` | `cross-zone egress` | GB |
| `consumption` | `egress to another region` | GB |
| `consumption` | `egress across an ocean` | GB |
| `consumption` | `spilled data on disk` | GB-month |
| `incidents` | `calls that did not answer in time` | reruns |
| `incidents` | `nodes lost` | failures |
| `incidents` | `nodes that filled up` | failures |
| `incidents` | `late finish` | seconds |

<Note>
**Capacity differs between the two sides.** The observed side has one named line per
node. The projected side has one system line because full-scale node count is itself
projected.
</Note>

## Bucket details


<AccordionGroup>
  <Accordion title="capacity">
    One line per node: `durationRefMs` converted to hours and multiplied by the
    instance's on-demand rate, with a billing minimum of 60 seconds by default.

    A node that received a `spot_notice` is billed at the spot rate, 70% off by
    default, and its line says `(c5.large, spot)`.

    Prices use **reference** time. The real run may take seconds, while the modeled
    job takes the duration shown by the simulated clock.
  </Accordion>
  <Accordion title="consumption">
    **Egress has three distances.** Traffic inside one zone is free. Traffic leaving
    the zone uses a rate based on its destination:

    | line | rate | when |
    |---|---|---|
    | `cross-zone egress` | `egress_per_gb` | another zone in the same region |
    | `egress to another region` | `egress_cross_region_per_gb` | another region on the same continent |
    | `egress across an ocean` | `egress_intercontinental_per_gb` | anything further |

    Read each node's `egressMb`, recorded by destination region as calls happen. A
    trace without that split is billed at the in-region rate.

    **Storage** is the worst node's `diskMb`, converted to GB-months for the period.
  </Accordion>
  <Accordion title="incidents">
    Counted from events: `rpc_timeout` as reruns, `kill` plus `spot_notice` as nodes
    lost, `oom` plus `disk_full` as nodes that filled up, and a per-second penalty
    past the service level.

    **Never scaled.** Projected incident lines use the observed counts. Three nodes
    lost in the run remains three nodes lost in the projected model.

    Treat projected incidents as *what this run cost*, not as a forecast of failures
    for the larger job.

  </Accordion>
  <Accordion title="build">
    The number of **distinct services** the system carries, multiplied by the monthly
    cost per service. The charge applies whether or not a service handles a call.
  </Accordion>
</AccordionGroup>

## Scaled runs

```
what happened
  build       services carried                      1.000 services       CHF    0.2500
  capacity    master (m5.2xlarge)                 0.01670 node-hours  CHF    0.0077
  capacity    w0 (r5.large)                       0.01670 node-hours  CHF    0.0025
  …
  consumption spilled data on disk              0.0001000 GB-month       CHF    0.0000
  ------------------------------------------------------------------------------------
  build        CHF       0.2500
  capacity     CHF       0.0177
  consumption  CHF       0.0000
  incidents    CHF       0.0000
  TOTAL COST   CHF       0.2677

what it is a model of
  build       services carried                      1.000 services       CHF    0.2500
  capacity    the system, for the period                 -                CHF   refused
      the ladder bends: over the lower half it grows as units^-0.20 and over the
      upper half as units^0.40, a difference of 0.60. Something behaves differently
      small than large, and no extrapolation across that means anything
  consumption spilled data on disk              0.0004000 GB-month       CHF    0.0000
  ------------------------------------------------------------------------------------
  build        CHF       0.2500
  capacity     CHF       0.0000
  consumption  CHF       0.0000
  incidents    CHF       0.0000
  TOTAL COST   CHF       0.2500   (of what could be priced)
```

Compare the two halves:

- `capacity` is per node on the left and one line on the right. The projected
  system size is not a list of observed nodes.
- `consumption` grew from 0.0001 to 0.0004 GB-month because storage has a fitted law.
- `incidents` did not move; the observed failures are carried across.
- `capacity` contributed `0.0000` because its projection was refused, so the total
  is labeled *of what could be priced*.

A refused line has no projected value. Capacity often depends on the measured
timeline, so it is a common source of uncertainty in the total.


Each projected quantity carries **its own** growth factor. Cross-zone bytes use the
wire law because crossing a zone depends on topology, not workload size. If the wire
law is refused, the line is refused instead of being printed as a full-scale value.
