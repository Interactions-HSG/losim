---
title: "scale"
description: "The relationship between measured run size and design size."
icon: "chart-line"
---

```yaml
scale: 5000
```

`scale` is the only scale setting. During a run, dissaly derives the probe ladder,
system sizes, and clock rate from it.

<ParamField path="scale" type="number" default="1">
  How many times larger the design is than the largest run the engine can measure.

  At **1**, dissaly runs the declared workload directly. `Load` receives exactly what
  [`input:`](/ref/input) declares, and the reported values are measurements.

  Above 1, dissaly measures a fraction of the input and projects from it. The fraction
  is `units / (scale x 8000)`, where 8000 is the top of the probe ladder. Thus
  `scale: 5000` represents a design 5000 times larger than the largest measured run.

  <Warning>
  The step from 1 to a larger value changes the result from a direct measurement to a
  projection. Only the projection has model error.
  </Warning>
</ParamField>

<Note>
**There is no `mode:` key.** `scale: 1` means direct measurement; a larger scale
means projection. A second setting would duplicate that distinction.

To compare a projection with a full run, use `scale: 1` and set `input.count` to the
full workload. This is valid but can be slow.
</Note>

## Units at different scales

<Warning>
`count:` is the workload in **your** unit, such as frames, lines, or orders. The
probe ladder's **units** are what handlers count with
`Dissaly.current().units(n)`. A handler that reports pixels per frame makes those
two quantities differ by a thousand, and nothing reconciles them.

The engine fits its laws in handler units and scales `count:` by the ratio between
rungs. The run reports both values and labels them:

```
thumbs-scaled.yaml  seed 5  scaled 4,800 -> 24,000,000 lines (x5,000)
  measured at 8,000 units — what the handlers counted with units(n), and what the
  laws below are fitted in
```

Before 3.0.1 the first line used ladder units, so `count: 24000000` could report a
different unit count from the configured input.
</Warning>

## Engine-selected values

<ParamField path="the probe ladder" type="1000, 2000, 4000, 8000">
  Four rungs. Three cannot show whether a law bends, and a bent law must be refused
  rather than extrapolated across. The engine selects the rungs independently of the
  design.
</ParamField>

<ParamField path="the system sizes" type="max(2, declared/2), max(3, declared)">
  Derived from the configured system. Probing a design at two workers when it is
  configured for eight would extrapolate across the measured system size.
</ParamField>

<ParamField path="the clock" type="20x at scale 1, up to 40x">
  See [the compressed clock](/engine/compressed-clock). The clock follows the scale
  and stops at 40x, where sleep debt and run timing remain stable.
</ParamField>

## Separate data and system ladders

<Warning>
A resource that grows with the **data** can look like one that grows with the
**system** when both vary together. Combining them would produce plausible but wrong
projections.

The grid therefore varies them on separate axes: the data ladder uses the system that
will run, while the system ladder holds the data constant.
</Warning>

## Probe grid

```
   data ladder      1k 2k 4k 8k    x  6 seeds   on the simulation's own system, calm
   system ladder    derived        x  2 seeds   at the middle data size,        calm
   weather column   the top size   x  2 seeds   the simulation's own failures
```

The grid uses about thirty runs. The data ladder uses six seeds. The law is fitted
on their median and checked by refitting **independent sets of two**.

The system ladder and weather column are cross-checks, so they use fewer seeds.

<Note>
**When the ladder crosses a threshold in your code.** If the design spills, switches
algorithms, or stops fitting in a cache between one and eight thousand units, the
engine sees a bent law and refuses it. Move the threshold or accept that the resource
cannot be projected across it.
</Note>

## Fault column

If any node declares `failures:`, the grid runs a weather column and adds an
**amplification** term. Work from a killed node is redone elsewhere, so a survivor
may absorb its share and increase peak memory.

With no weather declared, you get a note instead:

```
note: nothing in this simulation goes wrong, so the model carries no amplification
      term — a projection from it describes a system where nothing goes wrong
```

A model fitted only on clean runs under-predicts by that amount.
