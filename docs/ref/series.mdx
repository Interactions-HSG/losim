```json
"series": {
  "dtMs": 6.0,
  "t": [0.0, 6.0, 12.0, 18.0, …],
  "channels": {
    "w0.busyPct":  { "vm": "w0", "metric": "busyPct", "form": "runs",
                     "ticks": 402, "runs": [[0.0, 11], [100.0, 46], [50.0, 8]] },
    "w0.memCapMb": { "vm": "w0", "metric": "memCapMb", "form": "constant",
                     "ticks": 402, "value": 4096.0 },
    "w0.retainMb": { "vm": "w0", "metric": "retainMb", "form": "raw",
                     "ticks": 402, "raw": [0.0, 0.12, 1.44, …] }
  }
}
```

Channels are keyed `"<vm>.<metric>"`. `t` is shared by every channel — one array of
simulated times, `dtMs` apart.

## Why series exist at all

<Note>
A change log is **silent exactly when a system is stuck**, which is exactly when you
want to look at it. Series make the trace's size follow the run's **duration** rather
than its busyness, so a frozen fleet produces as much evidence as a working one.

The cadence is derived from `expectedRun` divided by 1000, floored at 1 ms — so a run
of any length yields a bounded number of ticks.
</Note>

The sampler runs on **its own thread**, not one of the machines' pool threads,
deliberately: what it costs must not land on the counters it is reading.

## The metrics

| metric | |
|---|---|
| `allocMb` | cumulative allocation by this machine's threads, losim's own subtracted |
| `retainMb` | what the machine is holding now — the retained-heap walk |
| `memCapMb` | its memory cap |
| `memPct` | `retainMb / memCapMb × 100` |
| `diskMb` | bytes declared through `wroteDisk`, cumulative |
| `diskPct` | against the disk cap |
| `inflight` | handlers **using** a core |
| `queued` | handlers **waiting** for one |
| `vcpu` | the machine's core count |
| `busyPct` | `inflight / vcpu × 100`, capped at 100 |
| `alive` | 1 or 0 |
| `frozen` | 1 or 0 |
| `degraded` | the current degrade factor, 1 when none |
| `bytesInMb`, `bytesOutMb` | cumulative |

<Warning>
`retainMb` **steps rather than glides**. A heap walk costs about 0.06 µs an object,
so a busy machine is walked every eighth tick rather than every tick. That is the
cadence, not your program.
</Warning>

## Three encodings

Most channels barely move — a machine is alive for the whole run, idle for most of
it, and its cap never changes at all. So each channel is stored in whichever of three
forms is smallest:

<ResponseField name="constant" type="every tick is the same value">
  ```json
  { "form": "constant", "ticks": 402, "value": 4096.0 }
  ```
</ResponseField>

<ResponseField name="runs" type="run-length encoded">
  ```json
  { "form": "runs", "ticks": 402, "runs": [[0.0, 11], [100.0, 46]] }
  ```
  Each pair is `[value, howManyTicks]`.
</ResponseField>

<ResponseField name="raw" type="one number per tick">
  ```json
  { "form": "raw", "ticks": 402, "raw": [0.0, 0.12, 1.44, …] }
  ```
</ResponseField>

Choosing the smallest is worth about two orders of magnitude, which is what lets the
richer trace come out **smaller** than the change log it replaced.

<Note>
Samples are quantised before encoding — a `…Pct` to one decimal place, a `…Mb` to
two. Without that a flat stretch is not flat: it jitters in the sixth decimal, no run
ever forms, and the encoding saves nothing.

That is also why the `machines` channel exists separately. Fitting a law against
numbers rounded to a hundredth of a megabyte would fit the rounding.
</Note>

## Decoding

```python
def channel(t, key):
    c = t["series"]["channels"][key]
    if c["form"] == "constant":
        return [c["value"]] * c["ticks"]
    if c["form"] == "runs":
        out = []
        for value, n in c["runs"]:
            out += [value] * int(n)
        return out
    return c["raw"]

import json
t = json.load(open("build/thumbs.json"))
times = t["series"]["t"]
busy  = channel(t, "w0.busyPct")
for at, b in list(zip(times, busy))[:10]:
    print(f"{at:8.1f}  {'#' * int(b / 5):<20} {b:5.1f}%")
```
