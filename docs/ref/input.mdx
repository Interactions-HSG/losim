```yaml
input:
  source: data/frames/     # a file, a folder, or left out entirely
  unit:   frame
  count:  30000
```

Three keys, and one of them is the only number the engine varies. This is what
losim hands `Job.Load` as a [`losim.Input`](/ref/losim-proto), with `count` already
shrunk to the size this run is measuring.

None of it is in anybody's Java, which is the point: a workload size written into a
constant cannot be swept, cannot be varied across a ladder, and makes a direct run a
different amount of work from the scaled run meant to model it.

<ParamField path="source" type="path">
  A file or a folder, relative to the project root. losim stats it at load and
  refuses a missing one on its own line, because a path is the one thing about a
  workload that can be checked before anything runs.

  A folder is the shape that survives scaling — one file per unit is how real input
  arrives.
</ParamField>

<ParamField path="unit" type="string" default="unit">
  What one item is, **singular**: `frame`, `line`, `order`. The same word
  `Losim.current().units(n)` counts and [`perUnit:`](/ref/simulated-duration)
  prices, so a blank one leaves three numbers counting something nobody named.
</ParamField>

<ParamField path="count" type="whole number" default="1">
  How many of them, **at full size**. Whole — *"a count that is not whole is one
  whose unit is wrong"* — and at least one, because zero is not a smaller run, it is
  no run.
</ParamField>

## Leaving out the source

Omitted, `Load` generates the workload from `Losim.current().seed()` and
`Input.count` instead. That is what a scaled workload should do anyway: reproducible
from the seed, varying with it across a sweep, and costing nothing on the clock
because `Load` is off it.

```yaml
input:
  unit:  order
  count: 50000
```

<Note>
**Not an executable.** A simulation that shells out to build its input stops being
reproducible from its seed, depends on the host's tools, and spends time
attributable to no node. Generating in `Load` is the same capability without any of
that.
</Note>

## What it is at scale

`count:` is the workload at **full** size. What a run actually does is that times
`units / (scale x 8000)` — which is 1 at `scale: 1`, and whichever rung the [scale
engine](/ref/scale) picked otherwise.

```yaml
scale: 6
input:
  unit:  line
  count: 48000
```

At the top rung of that ladder `Load` is asked for 8000 lines; at the bottom, 1000.
Nothing in `Input` says which, and `Run` never sees `Input` at all — a Job that could
tell a probe from the full size could behave differently at the two, and then the
projection would be a projection of nothing.

## Count versus loaded

`Load` returns a `Workload` carrying its own count, and it need not equal what it
was handed: a Job that folds duplicates or drops malformed rows produces fewer. The
trace records both, as `meta.count` and `meta.loaded`.

<Warning>
**They are only directly comparable at `scale: 1`.** `meta.count` is this file's
number, at full size; `meta.loaded` is what `Load` produced at whichever rung the
engine measured. Above `scale: 1` a `loaded` a sixth of `count` is a correct run of
a `scale: 6` simulation, not a `Load` losing five sixths of its input.

What `Load` was actually asked for is `count x scale.units / scale.fullUnits`, and
both of those are in the trace's `scale` block.
</Warning>

Read them anyway. A `Load` that quietly returns a tenth of what it was asked for is
how a fitted exponent goes wrong for a reason nobody finds.

## What is refused

| | |
|---|---|
| a `source:` that is not there | with the line it is on |
| a blank `unit:` | with the line it is on |
| `count:` below 1 | not a smaller run: no run at all |
| `count:` that is not whole | its unit is wrong; say what one item is |
| a count that shrinks to none at the chosen rung | refused rather than rounded up, which would change the ratios |

All of them before anything runs, so they read as a line to fix rather than a design
that fell over.

<Note>
An [overlay](/ref/cli-simulate) cannot change `input:`. An overlay changes the
weather; a simulation whose workload had been swapped out underneath it is no longer
a run of that design, and the two could not be compared.
</Note>

## Anything the program discovers as it runs does not belong here

A vocabulary, a count of distinct keys, a fan-out that depends on the data: those
are [revealed](/ref/api-losim) while `Run` works, and fitted against the count —
which is how the engine learns that one quantity saturates where another does not.
