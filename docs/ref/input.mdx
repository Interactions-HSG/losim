title: "input"
description: "The simulation input source, unit, and count."
icon: "inbox"
---

```yaml
input:
  source: data/frames/     # a file, a folder, or left out entirely
  unit:   frame
  count:  30000
```

These keys define the workload. losim passes them to `Job.Load` as a
[`losim.Input`](/ref/losim-proto); the engine adjusts `count` for the run's scale.

Keeping the workload here lets the engine vary its size across a scale ladder. A
constant in Java would make direct and scaled runs use different definitions.

<ParamField path="source" type="path">
  A file or folder relative to the project root. losim checks it before loading the
  workload and reports a missing path on its own line.

  A folder also supports one file per input unit, which is useful when the workload
  grows with the scale.
</ParamField>

<ParamField path="unit" type="string" default="unit">
  The singular name for one item, such as `frame`, `line`, or `order`. The same word
  names the units recorded by `Losim.current().units(n)` and priced by
  [`perUnit:`](/ref/simulated-duration).
</ParamField>

<ParamField path="count" type="whole number" default="1">
  How many items the full-size workload contains. The value must be a whole number
  of at least one.
</ParamField>

## No source

When `source` is omitted, `Load` generates the workload from
`Losim.current().seed()` and `Input.count`. The seed keeps sweeps reproducible, and
the loading work is outside the simulated clock.

```yaml
input:
  unit:  order
  count: 50000
```

<Note>
**Not an executable.** Building input through a host command adds an external tool
dependency and makes the result depend on the host. Generate it in `Load` instead.
</Note>

## Full and measured sizes

`count:` is the full-size workload. A run loads the portion selected by the
[`scale` engine](/ref/scale), using `units / (scale x 8000)` as the fraction in this
example.

```yaml
scale: 6
input:
  unit:  line
  count: 48000
```

At the top rung `Load` receives 8000 lines; at the bottom it receives 1000. `Run`
does not receive `Input`, so the Job cannot change behavior based on whether the
engine is probing or measuring the full workload.

## Count versus loaded

`Load` returns a `Workload` with its own count. That count can be lower than the
requested value when the Job removes duplicates or malformed rows. The trace stores
both values as `meta.count` and `meta.loaded`.

<Warning>
**They are directly comparable only at `scale: 1`.** `meta.count` is the full-size
value from this file. `meta.loaded` is what `Load` produced at the selected rung. At
`scale: 6`, a `loaded` value one sixth of `count` is expected.

The trace's `scale` block contains `scale.units` and `scale.fullUnits`, which show
the requested value as `count x scale.units / scale.fullUnits`.
</Warning>

Compare them when diagnosing a result. A `Load` that returns much less than
requested can distort the fitted exponent.

## Refused input

| | |
|---|---|
| a `source:` that is not there | with the line it is on |
| a blank `unit:` | with the line it is on |
| `count:` below 1 | not a smaller run: no run at all |
| `count:` that is not whole | its unit is wrong; say what one item is |
| a count that shrinks to none at the chosen rung | refused rather than rounded up, which would change the ratios |

losim checks all of these before the simulation starts.

<Note>
An [overlay](/ref/cli-simulate) cannot change `input:`. Overlays change runtime
conditions, not the workload definition being compared.
</Note>

## Values discovered at runtime

Values discovered during `Run`, such as a vocabulary, distinct-key count, or
data-dependent fan-out, belong in [revealed](/ref/api-losim). losim fits those values
against the input count.
