The schema has no top-level `failures:` key. Write each failure **inside its
target**, either a node or one RPC on one node.

```yaml
nodes:
  w9:
    instance: c5.large
    runs:
      Thumbnailer:
        file: src/Shrinker.java
        failures:                                        # rpc level
          Thumbnail:
            - { status: UNAVAILABLE, per: 20 calls }
    failures:                                            # node level
      - { kill: true, at: 400 refMs, restartAfter: 300 refMs }
      - { degrade: 3, per: 2 refSeconds }
      - { partition: master, at: 900 refMs }
```

Each entry describes **one** action. An entry with multiple actions is refused:
*"this failure does two things at once (kill and freeze); write them as two."*

## Schedule failures

<ParamField path="at: <duration>" type="an instant">
  It happens once at the specified time. The seed does not affect this schedule.
</ParamField>

<ParamField path="per: <duration> or <N> calls" type="a rate">
  A **mean** gap drawn exponentially using `-ln(1 - u) x per`. Each firing draws the
  next interval, so the rate continues for the duration of the run.

  At node level `per:` is a duration; at rpc level it is `N calls`, meaning one call
  in N.
</ParamField>

An entry with both schedules describes two failures as one and is refused. An entry
with neither schedule never fires and is also refused.

<Note>
A kill at 900 refMs tests one point in time. A rate tests failures throughout the run.
Use sweeps to evaluate multiple seeds. [Sweeps ->](/simulate/sweeps)
</Note>

## Node-level failures

Write these in the node's `failures:` list. The containing node is the target, so
these fields take no target.

<ParamField path="kill: true" type="node failure">
  The node stops answering. Callers find out by running out of time.

  `restartAfter: <duration>` brings it back after that interval. A restart scheduled
  **after the simulation has ended** is skipped. Ensure that `at + restartAfter`
  falls inside the run when the node must return.
</ParamField>

<ParamField path="freeze: true" type="node failure">
  A stop-the-world pause. Calls remain pending on the node's own threads, so the
  caller observes slowness rather than a failed call.

  `for: <duration>` (default `1000 refMs`) says how long. The thaw is scheduled
  independently, so a pause ends whether or not a call happened to be waiting.
</ParamField>

<ParamField path="degrade: <factor>" type="node failure">
  Every declared cost on this node is multiplied. The factor must exceed 1;
  *"a factor of 1 is a node that is not degraded."*

  This creates a slower node without stopping it.
</ParamField>

<ParamField path="spotReclaim: true" type="node failure">
  A `spot_notice` event fires, then the node is killed `notice:` later (default
  `0 refMs`). `restartAfter:` works here too.

  The bill prices a node that received a notice at the spot rate, which is 70% off by
  default. The node remains subject to reclaim.
</ParamField>

<ParamField path="partition: <other node>" type="node failure">
  Cuts the link between this node and that one, in **both directions**. Both stay
  alive and keep serving whoever they can still reach.

  This is the only kind that names another node. The other node must exist and
  cannot be the current node: *"'w1' is partitioned from itself."*
</ParamField>

<ParamField path="heal: <other node>" type="node failure">
  Restores the link.
</ParamField>

<ParamField path="restart: true" type="node failure">
  Brings a node back with **fresh service instances** and an empty
  `Losim.current().local()`, so whatever it was holding is gone.

  ```json
  { "kind": "restart", "vm": "w1",
    "detail": { "state": "lost",
                "note": "fresh services: whatever it was holding is gone" } }
  ```
</ParamField>

### Field defaults

| field | applies to | default |
|---|---|---|
| `at` or `per` | all | one of the two, required |
| `for` | `freeze` | `1000 refMs` |
| `notice` | `spotReclaim` | `0 refMs` |
| `restartAfter` | `kill`, `spotReclaim` | `0 refMs` (never) |

`per:` is accepted only on `kill`, `freeze`, and `degrade`. The other fields happen
once. A rate on one of them is refused with the line *"partition changes what
reaches what, and stays changed until the other one undoes it"*.

### Pool failures are per node

A `per: 2 refSeconds` on a pool of six gives each node its own failure schedule. It
does not select one shared node, and it remains per-node when the pool is resized.

To target one node in a pool, write the failure under `overrides:`. Each node's rate
also draws from its own stream, so adding a rule to one node leaves the schedules of
the other nodes unchanged. A sweep then compares the same failure schedule for each
node.

## RPC-level failures

Write these inside a `runs:` entry, keyed by the RPC they affect. RPC failures use
rates. A failure that begins at an instant and persists belongs to the node, and
`degrade` already covers that behavior.

```yaml
runs:
  Thumbnailer:
    file: src/Shrinker.java
    failures:
      Thumbnail:
        - { status: RESOURCE_EXHAUSTED, per: 20 calls }
        - { slow: 6, per: 50 calls }
      Pull:
        - { drop: true, per: 100 calls }
```

<ParamField path="status: <CODE>" type="rpc failure">
  The handler is never reached and no span opens; the caller gets that gRPC status.
  Any code except `OK`. *"OK is what a call that worked returns, so a failure cannot
  be one."*
</ParamField>

<ParamField path="slow: <factor>" type="rpc failure">
  This rpc's declared duration is multiplied on this node. Above 1.

This slows a **call path**, not the whole node. Selecting another peer can avoid it.
</ParamField>

<ParamField path="drop: true" type="rpc failure">
  The request never arrives. Decided on the caller's side, so the callee never sees
  it and the caller finds out by running out of time.
</ParamField>

Because they nest under one node's `runs:`, an RPC can fail **on one node while its
peers continue serving requests**. `overrides:` does not accept `runs:`, so write
that node on its own beside the pool:

```yaml
workers:
  count: 5
  prefix: w
  instance: c5.large
  runs: { Thumbnailer: src/Shrinker.java }

w9:                                        # the same service, the same file, one bad copy
  instance: c5.large
  runs:
    Thumbnailer:
      file: src/Shrinker.java
      failures:
        Thumbnail:
          - { status: UNAVAILABLE, per: 20 calls }
```

`peersServing("Thumbnailer")` finds all six. One of them has the RPC failure.

## RPC validation

The RPC name is checked at each stage of validation. The first check runs before
anything is compiled:

```
thumbs.yaml:19: failures names 'src/Shrinker.java Thumbnil', and src/Shrinker.java
serves no rpc of that name. It serves Thumbnail, Pull. A failure with no matching
RPC never fires, so the loader refuses it instead of issuing a warning.
```

[`losim check`](/ref/cli-losim) reads the `.proto` text before compilation. The loader
preserves the line number and loads no classes. Before any call, the run asks the
bound gRPC server to validate the RPC.

## In the trace

A drawn node failure writes its own event first, then the ordinary one:

```json
{ "kind": "failure", "vm": "w2",
  "detail": { "kind": "kill", "drawn": true, "atRefMs": 1843.2 } }
```

so the trace distinguishes scripted failures from drawn failures. Both use the same
event structure. RPC failures write `rpc_failure`, naming the method and the call it hit:

```json
{ "kind": "rpc_failure", "vm": "w3",
  "detail": { "kind": "status", "method": "Thumbnail",
              "status": "UNAVAILABLE", "call": "s41" } }
```

`drop` writes no callee event because the request never arrived.

## Failure clock

The clock is zeroed after in-process servers are built. A failure written at 120
refMs therefore occurs at 120 refMs in the trace, independent of setup time.
