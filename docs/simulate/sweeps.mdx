<Warning>
**Runs are not reproducible.** losim uses real threads and the wall clock rather than
simulating a scheduler, so repeated runs can have different durations and byte
counts.

A sweep is therefore the unit of evidence, not an individual run.
</Warning>

## Sweep Structure

**losim is a library, so a sweep is a Java program.** `Simulate.of` returns a result
object, which a sweep can process directly.

```java src/lab/Sweep.java
package lab;

import java.nio.file.Path;
import losim.runtime.Simulate;
import losim.sim.Loader;
import losim.trace.Telemetry;

public final class Sweep {

    public static void main(String[] args) throws Exception {
        var base = Loader.load(Path.of(args[0]));
        var loader = Thread.currentThread().getContextClassLoader();

        int completed = 0;
        double slowest = 0;

        for (long seed = 1; seed <= 20; seed++) {
            // OFF records completion and failure without trace details.
            var r = Simulate.of(base.withSeed(seed), loader, Telemetry.Level.OFF);
            if (r.completed()) completed++;
            else System.out.printf("seed %2d  %s%n", seed, r.failure());
            slowest = Math.max(slowest, r.durationRefMs());
        }

        System.out.printf("%d of 20 finished, worst %.0f refMs%n", completed, slowest);
    }
}
```

<Note>
**An incomplete run remains a data point.** `Simulate.of` returns normally for both
outcomes; `completed()` reports the result and `failure()` gives the reason. A run
that cannot start still throws and stops the sweep.
</Note>


## Reading a sweep

```python summarise.py
import glob, json, statistics, sys

rows = []
for f in sorted(glob.glob(sys.argv[1] + "/*.json")):
    t = json.load(open(f))
    meta = t["meta"]
    events = t["events"]
    kinds = {}
    for e in events:
        kinds[e["kind"]] = kinds.get(e["kind"], 0) + 1
    rows.append({
        "seed":      meta["seed"],
        "completed": meta.get("completed", False),
        "refMs":     meta.get("durationRefMs", 0),
        "timeouts":  kinds.get("rpc_timeout", 0),
        "retries":   kinds.get("retry", 0),
        "oom":       kinds.get("oom", 0),
        "peakMb":    max((m["memoryMb"] for m in t["nodes"]), default=0),
    })

ok = [r for r in rows if r["completed"]]
print(f"{len(ok)}/{len(rows)} completed")
if ok:
    d = sorted(r["refMs"] for r in ok)
    print(f"  duration   median {statistics.median(d):8.0f} refMs   "
          f"worst {d[-1]:8.0f}   best {d[0]:8.0f}")
    m = sorted(r["peakMb"] for r in ok)
    print(f"  peak held  median {statistics.median(m):8.2f} MB     worst {m[-1]:8.2f}")
print(f"  timeouts   total {sum(r['timeouts'] for r in rows)}")
print(f"  OOMs       total {sum(r['oom'] for r in rows)}")
```

```
17/20 completed
  duration   median     2503 refMs   worst     6104   best     2311
  peak held  median     6.82 MB      worst    13.44
  timeouts   total 41
  OOMs       total 3
```

<Note>
**Report the spread across runs.** A design with median 2503 and worst 6104 has
different operational behavior from one that takes 2900 every time. The spread is
what matters for a service level.
</Note>

## Sweep axes

These values draw from the seed:

| | |
|---|---|
| a failure written with `per:` | the gaps between firings — drawn exponentially, per node |
| an rpc failure's `per: N calls` | which calls it hits |
| network jitter | how each round trip falls |
| packet loss | which messages vanish |
| **your workload** | if your `Load` took `Losim.current().seed()`, which is why it should |

A failure written with `at:` does **not** vary. A kill at 900 refMs occurs at that
time for every seed. Use `at:` for fixed scenarios and `per:` for repeated failure
trials.

## Sweeping another axis

The simulation is an object, so change one property while leaving the others intact:

```java
var base = Loader.load(Path.of("thumbs.yaml")).withoutWeather();
var loader = Thread.currentThread().getContextClassLoader();

for (int workers : new int[] {2, 4, 8}) {
    var r = Simulate.of(base.withWorkers(workers), loader, Telemetry.Level.OFF);
    System.out.printf("%2d workers  %8.0f refMs  %s%n",
            workers, r.durationRefMs(), r.completed() ? "completed" : "did not");
}
```

```
 2 workers      2131 refMs  completed
 4 workers      1708 refMs  completed

 8 workers      1572 refMs  completed
```

<Note>
`withWorkers` resizes **every pool that had more than one node**, keeping its
instance type, zones, and services. Singletons such as the master are unchanged.

Other axes include `withUnits`, `withSeed`, `withKTime`, `withExpectedRun`, and
`withoutWeather`. Each returns a copy, so the loaded base is unchanged and each run
differs by one setting.
</Note>


Read `durationRefMs` and the bill from each result. The curve shows how runtime
changes as the system changes.

<Tip>
Vary **one axis at a time**. If system size and workload change together, a resource
that grows with one is indistinguishable from a resource that grows with the other.
The scale engine separates these axes for the same reason.
</Tip>
