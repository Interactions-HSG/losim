Compare the simulation files. Code is referenced by class name rather than embedded
in the simulation file.

## Comparison rules

<Steps>
  <Step title="Change one thing">
    Two simulations that differ in the system **and** the job are separate
    experiments. When comparing jobs, keep the system identical; when comparing
    systems, keep the job identical.
  </Step>
  <Step title="Use the same declared costs">
    A handler declared at 3 refMs in one design and 30 in the other compares two cost
    claims, not two designs. Keep declared costs the same.
  </Step>
  <Step title="Sweep both, not run both">
    Use twenty seeds for each design. One run can differ more than the designs do.
  </Step>
  <Step title="Read the bill, not the clock">
    Use the bill as well as runtime. Two designs with the same runtime can differ by
    an order of magnitude in egress.
  </Step>
</Steps>

## Runtime comparison

```bash
java -cp "$CP" losim.cli.Main simulate design-a.yaml --cp build/losim/classes --out build/results/a.json
java -cp "$CP" losim.cli.Main simulate design-b.yaml --cp build/losim/classes --out build/results/b.json
```

Open `a`, then pick `b` from **`compare with…`**. Both runs use
[one clock](/viewer/views#two-runs-on-one-clock) in absolute refMs, so their finish
times can be compared directly. The viewer also shows each run's cost.

The runtime view shows *when* and *where* the designs diverge. The bill shows *what*
caused the cost.

## Bill comparison


```bash
java -cp "$CP" losim.cli.Main bill build/design-a.json > build/a.bill
java -cp "$CP" losim.cli.Main bill build/design-b.json > build/b.bill
diff -y --width=160 build/a.bill build/b.bill
```

The billing buckets are printed separately. A design can increase **capacity** and
**build** cost while reducing **incidents**; one total would hide that trade.

<Tip>
Distort a price to find out what a design is really sensitive to. Copy
`prices/eu-central-1.yaml`, make egress ruinous, and re-bill **the same traces**:

```yaml prices/expensive-egress.yaml
egress_per_gb: 4.00
```

```bash
java -cp "$CP" losim.cli.Main bill build/design-a.json --prices prices/expensive-egress.yaml
```

Billing is a pure function of the trace, so this needs no re-run. If the ranking
changes, the original advantage depended on the price assumption.
</Tip>

## Checks performed by `losim compare`

```bash
java -cp "$CP" losim.cli.Main compare build/a.json build/b.json
```

<Warning>
`compare` answers **"are these two the same simulator?"** It does not decide which
design is better. Use it to check whether different environments produce the same
structural trace, including in CI.
</Warning>

It splits everything it compares into two kinds:

<Columns cols={2}>
  <Card title="Structural — must agree" icon="lock">
    The schema version. The simulation, job, seed, `scale`, telemetry level, mode.
    Which nodes existed. Which sampled channels exist. What each kind of event
    **carries**. What each span kind is labelled. **What each resource was found to
    be a function of**, and what the engine refused.

    A difference here means the environments are not running the same simulator.
  </Card>
  <Card title="Measured — printed, not judged" icon="ruler">
    The duration. The run size the engine chose. Every fitted exponent.

    Runs and hosts vary, so these values are reported but not used for structural
    equality.
  </Card>
</Columns>

```
build/results-runner/t10.json
build/results-codespace/t10.json

  same    schema
  same    meta.simulation
  same    what each event kind carries
  same    what each resource is a function of
  same    what the engine refused
  differs meta.durationRefMs          4820 vs 6113
  differs exponent of memoryMb        1.013 vs 1.011
```

<Note>
The **`what each resource is a function of`** line is structural: attribution is a
fact about the program and should not depend on the host. Exponent differences are
measurements and are reported rather than judged.
</Note>

## Design results

Use a separate summary for design results:

```python compare.py
import glob, json, statistics, sys

def summarise(pattern):
    runs = [json.load(open(f)) for f in glob.glob(pattern)]
    ok = [t for t in runs if t["meta"].get("completed")]
    return {
        "runs":      len(runs),
        "completed": len(ok),
        "medianRefMs": statistics.median([t["meta"]["durationRefMs"] for t in ok]) if ok else None,
        "p90RefMs":  sorted(t["meta"]["durationRefMs"] for t in ok)[int(len(ok) * 0.9)] if ok else None,
        "peakHeldMb": max((m["memoryMb"] for t in ok for m in t["nodes"]), default=0),
        "crossZoneMb": statistics.median(
            [sum(m["crossZoneMb"] for m in t["nodes"]) for t in ok]) if ok else 0,
        "timeouts":  sum(1 for t in runs for e in t["events"] if e["kind"] == "rpc_timeout"),
    }

a, b = summarise(sys.argv[1]), summarise(sys.argv[2])
for k in a:
    print(f"  {k:<14} {str(a[k]):>14}   {str(b[k]):>14}")
```

```
  runs                       20               20
  completed                  17               20
  medianRefMs              2503             2881
  p90RefMs                 5940             3102
  peakHeldMb              13.44             7.11
  crossZoneMb             0.912            0.088
  timeouts                   41                4
```

Design B is slower at the median and **better** on the other reported measures. A
multi-run summary is needed to see this trade-off.
