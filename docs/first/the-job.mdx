A simulation declares nodes and weather. Everything that is code is a gRPC service,
including the thing that starts the work.

losim ships that one in its own schema: [`losim.Job`](/ref/losim-proto), with two
rpcs. `Load` builds the workload off the clock; `Run` is the simulation. You
implement it exactly the way you implement `Thumbnailer` — extend the `ImplBase`
protoc generated, and let a node run it.

```yaml
nodes:
  coordinator:
    instance: m5.large
    runs: { losim.Job: src/lab/RenderJob.java }
```

## The whole thing

```java src/lab/RenderJob.java
package lab;

import com.google.common.util.concurrent.ListenableFuture;
import com.google.protobuf.InvalidProtocolBufferException;
import io.grpc.stub.StreamObserver;
import java.util.*;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.TimeUnit;
import lab.pb.*;
import losim.api.Losim;
import losim.pb.Input;
import losim.pb.JobGrpc;
import losim.pb.Result;
import losim.pb.Workload;

public final class RenderJob extends JobGrpc.JobImplBase {

    private static final int FRAMES_PER_BATCH = 25;   // how it batches, not how big the album is

    /** Off the clock. Nothing spent here is charged to anybody. */
    @Override public void load(Input in, StreamObserver<Workload> out) {
        Album album = Albums.of(in.getCount(), Losim.current().seed());
        out.onNext(Workload.newBuilder()
                .setCount(album.getFrameCount())
                .setType(Album.getDescriptor().getFullName())
                .setPayload(album.toByteString())
                .build());
        out.onCompleted();
    }

    /** The simulation. Everything in here is measured. */
    @Override public void run(Workload work, StreamObserver<Result> out) {
        var here = Losim.current();
        Album album;
        try {
            album = Album.parseFrom(work.getPayload());     // your cost, on the clock
        } catch (InvalidProtocolBufferException e) {
            out.onError(e);
            return;
        }

        // 1. Who can do the work? By what they serve, never by hostname.
        List<String> workers = here.peersServing("Thumbnailer");
        if (workers.isEmpty()) throw new IllegalStateException("nobody serves Thumbnailer");
        here.log(workers.size() + " nodes can make thumbnails");

        // 2. How big is each of them? You cannot look, so you ask.
        var capacity = new LinkedHashMap<String, Health>();
        for (String worker : workers) {
            var stub = ThumbnailerGrpc.newBlockingStub(here.channelTo(worker))
                                      .withDeadlineAfter(500, TimeUnit.MILLISECONDS);
            capacity.put(worker, stub.capacity(Empty.getDefaultInstance()));
        }
        here.reveal("peers", capacity.size());

        // A share per node, proportional to its cores. Crude on purpose.
        var share = new ArrayList<String>();
        capacity.forEach((name, health) -> {
            for (int i = 0; i < Math.max(1, health.getVcpu()); i++) share.add(name);
        });

        // 3. Fan out. Every call is asynchronous, so they overlap.
        int thumbs = 0, failed = 0;
        var inflight = new ArrayList<ListenableFuture<Thumbs>>();
        var frames = album.getFrameList();

        for (int i = 0; i * FRAMES_PER_BATCH < frames.size(); i++) {
            var batch = Batch.newBuilder().addAllFrames(frames.subList(
                    i * FRAMES_PER_BATCH,
                    Math.min(frames.size(), (i + 1) * FRAMES_PER_BATCH))).build();

            String worker = share.get(i % share.size());
            var stub = ThumbnailerGrpc.newFutureStub(here.channelTo(worker))
                                      .withDeadlineAfter(2_000, TimeUnit.MILLISECONDS);
            inflight.add(stub.thumbnail(batch));
        }

        for (ListenableFuture<Thumbs> f : inflight) {
            try {
                thumbs += f.get().getThumbsCount();
            } catch (ExecutionException e) {
                // A node that has gone is a node that stopped answering,
                // and finding that out costs a call and a deadline.
                failed++;
                here.log("a batch did not come back: " + e.getCause().getMessage());
            }
        }

        // 4. The answer, structurally rather than as a line of text.
        out.onNext(Result.newBuilder()
                .putAnswer("thumbnails", String.valueOf(thumbs))
                .putAnswer("framesIn", String.valueOf(frames.size()))
                .putAnswer("batchesLost", String.valueOf(failed))
                .build());
        out.onCompleted();
    }
}
```

`Album` is one of **your** messages, in your `.proto`, holding a repeated `Frame`.
Building it needs nothing losim-specific:

```java src/lab/Albums.java
package lab;

import com.google.protobuf.ByteString;
import java.util.Random;
import lab.pb.Album;
import lab.pb.Frame;

final class Albums {
    static Album of(long frames, long seed) {
        var rng = new Random(seed);              // the simulation's seed, not one of our own
        var out = Album.newBuilder();
        for (int i = 0; i < frames; i++) {
            int w = 320 + rng.nextInt(1600), h = 240 + rng.nextInt(1200);
            byte[] pixels = new byte[w * h / 64];
            rng.nextBytes(pixels);
            out.addFrame(Frame.newBuilder().setId("f" + i).setWidth(w).setHeight(h)
                    .setPixels(ByteString.copyFrom(pixels)));
        }
        return out.build();
    }
}
```

## Why the work is split across two rpcs

<Note>
**`Load` is free and `Run` is not.** Reading a folder of frames, or generating an
album from the seed, is not part of the design being measured — so losim calls
`Load` with the clock stopped and resets every node's ledger before `Run` starts.
Nothing `Load` allocated is on anybody's bill, and nothing it did is in the trace.

Parsing the payload in `Run` **is** on the clock, and that is the honest line:
reading your input is losim's cost, unpacking it is your design's.
</Note>

<Warning>
**`Run` cannot see the simulation.** It receives a `Workload` — a count and some
bytes — and nothing else. It cannot read `input:`, cannot see the `source:`, and
cannot tell a probe run from the full one.

That is deliberate, and the whole scale model rests on it. A Job that could tell
which size it was doing could behave differently at the two, and then the
projection would be a projection of nothing.
</Warning>

## Each `Losim.current()` call's payoff

<AccordionGroup>
  <Accordion title="peersServing(…) — peers by what they offer" icon="magnifying-glass" defaultOpen>
    Dead nodes are not listed. That is discovery working, **not** a liveness
    check: no real network offers you one, and a design that depends on knowing
    whether a peer is alive is a design that will not survive contact with a real
    network. A node that has gone is a node that has stopped answering, and
    finding that out still costs a call and a deadline — which is exactly what
    happens in step 3 when a batch does not come back.

    The argument is the **service name from your `.proto`** — `Thumbnailer` — which
    is also the key its node wrote in `runs:`. Not the Java class, and not the file
    path. [More ->](/write/finding-peers)
  </Accordion>

  <Accordion title="channelTo(…) — a channel with losim on it" icon="plug">
    What comes back is an ordinary `io.grpc.Channel`, and the call site is plain
    gRPC. The node owns the channel, makes it once and keeps it, so your code
    never sees a lifetime.

    A channel you build yourself with `ManagedChannelBuilder` has none of losim's
    interceptors attached: the call happens at full speed, costs no bytes, waits
    out no latency, survives a partition, and leaves nothing in the trace to say
    it happened. That is why the verifier flags it.
  </Accordion>

  <Accordion title="seed() — where a generated workload comes from" icon="dice">
    A `Load` that has no `source:` to read generates from here, and it has to come
    from here: a sweep of seeds is meant to vary the *data* as well as the weather,
    and a workload that draws from a constant of its own is a workload whose every
    run is the same afternoon.
  </Accordion>

  <Accordion title="reveal(…) and log(…) — narration" icon="comment">
    `reveal` records a named value in the trace; `log` records a line. Both land
    inside the span they were called from, so a reader can see what the computation
    was doing and not merely that it happened. [More ->](/write/telemetry)
  </Accordion>

  <Accordion title="local() — what this node is holding" icon="box-archive">
    A map shared by every service on this node, reachable from no other, and
    **emptied by a restart**. For a cache or an index that two of your services both
    need. Free in time; not free in memory — whatever it holds counts against the
    node's cap. [More ->](/write/memory)
  </Accordion>
</AccordionGroup>

## Where the spans come from

There is no `phase` and no `compute`. `Run` is a handler, so it already has a span
— the trace's **root** — and everything the Job does nests beneath it: every call it
makes, and every handler those calls reach.

Work the Job does on its own, like parsing the payload, is inside that root span and
occupies one of the coordinator's cores while it happens, because `Run` queues and
occupies a thread like any other call. Give that node headroom.

If you want a stretch of work to have a name in the trace, make it a call to a
service that does it. That is a thing the trace, the bill and the critical path can
all already see.

## Two things this job does that are worth copying

**Every outbound call has a deadline.** `withDeadlineAfter(2_000, MILLISECONDS)`
means 2000 *reference* milliseconds, like every other duration — losim rewrites it
into real time so it survives `k_time`. A call with no deadline waits five seconds
and then gives up on your behalf, and the trace says that is what happened.

**The fan-out is asynchronous.** `newFutureStub` dispatches every batch and then
collects. With `newBlockingStub` in the loop, four nodes would be used strictly one
at a time, the answer would be correct, and the whole exercise would teach nothing.
This is the single most common way a first system turns out to be sequential — and
the [Spans view](/viewer/views) makes it obvious in one glance.
