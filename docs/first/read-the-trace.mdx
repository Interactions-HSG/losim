## Three channels

A change log records transitions. It cannot show a system that remains in one
state, so the trace has separate channels for events, intervals, and sampled
state.

<Columns cols={3}>
  <Card title="events" icon="bolt">
    Sparse records for individual moments, such as a node being killed, a call
    timing out, or a handler receiving 25 frames.
  </Card>
  <Card title="spans" icon="bars-staggered">
    Intervals that carry a **parent across the RPC boundary**. The resulting
    span tree shows how one distributed call led to another.
  </Card>
  <Card title="series" icon="chart-area">
    Numbers sampled at a fixed cadence. This channel records what the system was
    holding while no discrete event occurred.
  </Card>
</Columns>

## Start with three questions

<Steps>
  <Step title="Did the work actually overlap?">
    Look at the `handler` spans. If `w0`'s handler always ends before `w1`'s
    begins, the fan-out is sequential. The extra nodes are not doing work at
    the same time.

    ```bash
    python3 -c "
    import json; t = json.load(open('build/thumbs.json'))
    h = [s for s in t['spans'] if s['kind'] == 'handler']
    print('handlers:', len(h))
    print('span of time:', min(s['t0'] for s in h), '->', max(s['t1'] for s in h))
    print('busy time summed:', round(sum(s['t1'] - s['t0'] for s in h), 1))
    "
    ```

    When summed busy time is much larger than the wall span, handlers overlapped.
    When the two values are close, the work formed a queue.
  </Step>

  <Step title="Did every node get work?">
    ```bash
    python3 -c "
    import json, collections; t = json.load(open('build/thumbs.json'))
    print(collections.Counter(m['name'] + ':' + str(m['calls'])
          for m in t['nodes']))
    "
    ```

    A node with zero calls usually points to a discovery problem: the service
    name may be wrong, or the master may have discovered and cached peers
    only once.
  </Step>

  <Step title="Did anything queue, or fill up?">
    A `queue_wait` event means that a call waited for a core. A few are normal.
    Many waits on one node usually mean that placement ignores the nodes'
    capacities. That is easy to trigger when the system includes an
    `a1.medium`.

    `oom` and `disk_full` events identify the node, resource, cap, and
    **measured** demand.
  </Step>
</Steps>

## Format details

<Warning>
**`method` is dotted.** gRPC writes `lab.Thumbnailer/Thumbnail`; the trace writes
`lab.Thumbnailer.Thumbnail` so downstream tools can split the name on a dot. Use
the dotted form when matching method names.

**Payload collections are truncated at 12 entries** with a `"+1106 more"` marker.
The real count is the retained entries plus the marker count, not the number of
entries shown. A `Split` of 25 frames therefore renders as 12 frames and a
marker.
</Warning>

## The `nodes` array

The `nodes` array summarizes the run. It records peak retained memory, total
disk, bytes in and out, cross-zone bytes, handled calls, and the caps applied to
each node.

It is separate from the event channel because these values describe the whole
run rather than individual moments. Billing, comparisons with ground truth, and
the node table in the viewer can use them directly instead of reconstructing
peaks from a sampled series.

<Note>
`memoryMb` is **peak retained heap**, or what the node was still holding.
`allocMb` is the total amount it allocated over the run. They answer different
questions, and only `memoryMb` determines whether the node runs out of memory.
Accumulating data and streaming it can have similar allocation totals while
having very different retained-memory peaks.
</Note>

## View the trace

Everything on this page is a question you can also answer by watching the run:

```bash
java -cp "$CP" dissaly.cli.Main simulate thumbs.yaml \
     --cp build/dissaly/classes --out build/results/thumbs.json
```

The viewer makes the same three checks visual: overlapping work, work assigned
to each node, and queued or rejected operations. Its scrubber marks the moments
when something went wrong. [Open the viewer](/viewer/index)
