```bash
java -cp build/dissaly.jar dissaly.cli.Main bill build/thumbs.json
```

This example includes one killed node and one slowed node.

<Note>
**Your figures will not match these exactly.** dissaly runs your code on real
threads, so event-level results vary between runs ([system boundary](/engine/system-boundary)).
Timeout counts are especially sensitive to the host. Compare the large buckets
and the rows that appear rather than expecting identical event counts.
</Note>


```
build/thumbs.json

what happened
  build       services carried                     0.0700 service-months CHF       17.50
  capacity    master (m5.large)                     50.40 node-hours     CHF        5.80
  capacity    w0 (c5.large)                         50.40 node-hours     CHF        5.14
  capacity    w1 (c5.large)                         50.40 node-hours     CHF        5.14
  capacity    w2 (c5.large)                         50.40 node-hours     CHF        5.14
  capacity    w3 (a1.medium)                        50.40 node-hours     CHF        1.29
  consumption cross-zone egress                     1,987 GB             CHF       19.87
  consumption same-zone egress                      3,542 GB             CHF       17.71
  ------------------------------------------------------------------------------------
  counted, and not priced
              calls that did not answer in time     40.00 calls          not priced
              nodes lost                            1.000 nodes          not priced
              late finish                           2.100 seconds        not priced
  ------------------------------------------------------------------------------------
  build        CHF       17.50
  capacity     CHF       22.51
  consumption  CHF       37.58
  TOTAL COST   CHF       77.59
```

Read these three details before looking at the bucket definitions.

**A run of 2.1 seconds is billed as 2.1 days.** Every node shows `50.40`
node-hours, which is `2.1 x 24`. One second of the simulated clock stands for a
day of operation ([`billed_days_per_second`](/ref/prices)), because a cluster of
five priced at two seconds comes to four centimes and nobody argues with four
centimes. Traffic is scaled the same way — it is a flow, and it flowed for the
whole period.

**Capacity is one line per node, with the instance type shown.** `w3` is the
`a1.medium` configured in the simulation. It costs a quarter of its neighbours
for the same reserved period. This row connects the instance choice to the bill.

**The kill and the timeouts have no price.** They are counted under the rule, and
the total above them does not include them. What forty unanswered calls cost an
organisation is not a number this course has; how many there were is.

<Warning>
Two of the three buckets are decided before the work starts. Capacity is the
period you reserved and build is the design you carry, so making the job *faster*
moves neither — only `consumption` responds to a better algorithm, which is why
it is the line worth tuning against.
</Warning>

<Tip>
**Comment out the `failures:` blocks and bill the run again.** The money barely
moves: the kill and the slowdown cost you time, and time here is capacity, so the
difference is whatever the run's duration changed by. What *does* move is the
counted list, which empties. Read the two together — a fault-tolerance mechanism
is bought with build and capacity, and what it buys is the empty list.
</Tip>




## Three separate buckets

<Columns cols={3}>
  <Card title="capacity" icon="server">
    The system for the reserved period. **An idle node costs exactly as much as a
    busy one.** Capacity is priced in reference time, not in the wall-clock
    seconds used to run the simulation.
  </Card>
  <Card title="consumption" icon="gauge">
    Resources consumed by the work: egress and storage. Traffic inside one zone is
    cheaper than traffic between two, and neither is free.
  </Card>
  <Card title="build" icon="hammer">
    Engineering time to build and maintain the design, spread over its life and
    counted once per distinct service. This cost exists whether or not a failure
    occurs.
  </Card>
</Columns>

<Note>
**What broke is counted beside the money and never in it.** There used to be a
fourth bucket that priced it — a franc a second for finishing late, two rappen a
timeout — and on a run where every worker died those invented rates were 99% of
the bill. The total then said more about the rates than about the design.
</Note>

<Note>
There is no storage line because this system does not write to disk. A line
appears when the run records a quantity for that resource. After adding
`Dissaly.current().wroteDisk(bytes)`, the consumption bucket gains a `GB-month`
row.
</Note>

Adding the buckets hides design trade-offs. Replication triples capacity and adds
to build, and what it buys is on the counted list rather than in the total. The
printed total includes only quantities that the run could price.

## Price data

Price files live in [`prices/`](/ref/prices), outside the simulator. You can
change them or use deliberately distorted values for an exercise. For example,
make egress expensive and compare the designs:

```yaml prices/expensive-egress.yaml
egress_per_gb: 4.00        # instead of 0.01
```


```bash
java -cp build/dissaly.jar dissaly.cli.Main bill build/thumbs.json \
     --prices prices/expensive-egress.yaml
```

<Note>
**The price list does not contain node rental costs.** Those costs belong in the
instance catalogue with the vCPU and memory values because they describe the
node. Keeping one value in two places would allow the definitions to diverge.
</Note>

## When capacity is refused

Run a scaled simulation and dissaly can produce **two** bills: one for the observed
run and one for the workload it represents. The projected bill is conditional:
the engine refuses to extrapolate quantities it cannot estimate reliably.

```
  capacity    the system, for the period            -             CHF   refused
      its exponent moves by 0.793 between independent seed sets of the same
      workload, which over a factor of 6 is an error bar of x4.1 — wider than
      anything it would be asked to distinguish
```

Capacity depends on the timeline, which is the noisiest quantity dissaly measures.
It is also often the largest bill line. The result may therefore price bytes and
storage while refusing to price nodes because the job duration is not reliable.

The refusal identifies which part of the cost remains uncertain.

<Note>
**Counts are never projected.** A node either failed or did not. Extrapolating a
failure count from one run would create a forecast rather than an observation, so
the projected bill carries none of them — only its own makespan, and therefore how
late that finishes.
</Note>
