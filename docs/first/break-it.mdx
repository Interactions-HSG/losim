A scenario where nothing goes wrong tests nothing worth testing. Add this to
`thumbs.yaml`:

```yaml thumbs.yaml
faults:
  # After the survey and in the middle of the work, so the coordinator has to
  # notice a machine that is simply not there any more.
  - { at: 900 refMs, kill: w1 }

  # A noisy neighbour. Four times slower, and it does not die — which is the
  # failure most designs handle worst.
  - { at: 1200 refMs, degrade: w2, factor: 4 }
```

Run it again.

## The failure, in order

```
thumbs.yaml  seed 7  completed in 3980 refMs
  1102 events, 340 spans, 68 series -> build/thumbs.json
```

Look at what the coordinator logged:

```
a batch did not come back: w1 did not answer (unreachable)
a batch did not come back: w1 did not answer (unreachable)
a batch did not come back: w1 did not answer (unreachable)
```

Three batches lost, and each one cost the coordinator **its full 2000 refMs
deadline** before it found out. The run went from 2416 refMs to 3980.

<Note>
That is the lesson, and it is not a bug in losim. A dead machine, a cut link and a
lost packet are **one event from the caller**: nothing answers, and you find out by
running out of time. Modelling any of them as an immediate `UNAVAILABLE` would turn
the most instructive failure in distributed systems (you cannot tell a slow peer
from a gone one) into a tidy error code.
</Note>

## The three ways a message never arrives

<CodeGroup>
```yaml the machine is gone
faults:
  - { at: 900 refMs, kill: w1 }
```

```yaml the link is cut
faults:
  - { at: 900 refMs,  partition: [coordinator, w1] }
  - { at: 2500 refMs, heal:      [coordinator, w1] }
```

```yaml the packet is dropped
network:
  loss: 0.02      # 2% of messages simply never arrive
```
</CodeGroup>

All three produce the same thing at the call site: a `rpc_timeout` event and a
`DEADLINE_EXCEEDED` status, with `why` recording which it actually was — so the
trace can tell them apart even though your program could not.

## The whole catalogue of weather

| | what it does |
|---|---|
| `kill: w1` | the machine stops answering. Add `restart_after: 400 refMs` to bring it back. |
| `freeze: w1` + `for: 300 refMs` | a stop-the-world pause. Calls **do not fail**; they wait, on the machine's own threads, which is why a freeze is so much harder to diagnose than a crash. |
| `degrade: w2` + `factor: 4` | every declared cost multiplied. A straggler rather than a casualty. |
| `spot_reclaim: w0` + `notice: 200 refMs` | the machine tells you it is going, then goes. A design that ignores the warning deserves what happens. |
| `partition: [a, b]` / `heal: [a, b]` | the link between two machines, cut and restored. |
| `restart: w1` | back from the dead. What it remembers depends on how it was registered. |

## Standing chaos, instead of a scripted afternoon

A fault at 900 refMs teaches the fleet to survive 900 refMs. A **rate** teaches it
to survive whenever:

```yaml
chaos:
  - kill:   { every: 800 refMs, among: workers }
  - freeze: { every: 400 refMs, among: workers, for: 150 refMs }
```

`among:` is a pool name — `workers` — or one machine's name. The gaps are drawn
exponentially from the seed, so they vary the way real bad afternoons do.

<Warning>
Chaos is only drawn out to `expectedRun`. If your run overruns the horizon,
nothing happens to the fleet after it — a quiet second half that looks exactly
like a fleet behaving well. The trace says so with an `over_horizon` event, and
this is why that event exists.
</Warning>

**One seed is an anecdote.** A sweep is not a shell loop — losim is a library, so
write it in the language you are already in:

```java src/lab/Sweep.java
package lab;

import java.nio.file.Path;
import losim.runtime.Run;
import losim.scenario.Loader;

/** One seed is an anecdote. Twenty is a result. */
public final class Sweep {

    public static void main(String[] args) throws Exception {
        var base = Loader.load(Path.of("thumbs.yaml"));
        int completed = 0;

        for (long seed = 1; seed <= 20; seed++) {
            var result = Run.of(base.withSeed(seed));
            if (result.completed()) completed++;
            else System.out.printf("seed %2d  %s%n", seed, result.failure());
        }
        System.out.printf("%d of 20 finished%n", completed);
    }
}
```

`Loader.load` reads the scenario you already wrote; `withSeed` returns a copy with one
thing changed; `Run.of` runs it in this JVM and hands back the result as an object.
Nothing is written to disk, nothing is parsed back, and a seed that failed prints
**why** rather than becoming an indistinguishable `false`.

<Tip>
`withSeed` has siblings — `withRecords`, `withWorkers`, `withoutWeather`, `withKTime`,
`withExpectedRun`. Any of them is an axis you can sweep the same way, which is how you
ask *"is this a bad seed or a bad design?"*

For a long sweep, hand in `Telemetry.Level.OFF`
(`Run.of(scenario, loader, Telemetry.Level.OFF)`) — a sweep asks whether the run
finished, not what happened inside it, and building a full trace twenty times is the
slow part.
</Tip>


## Now make it survive

The obvious fix is a shorter deadline plus a retry, and losim will stop you here.
That is the point:

```yaml
retries:
  - { method: Thumbnail, attempts: 3, backoff: 50 refMs, multiplier: 2 }
```

This one is allowed, because `Thumbnail` declared `NO_SIDE_EFFECTS` in the
`.proto`. Try it on a method that declared nothing and the run refuses at load,
naming the file and the line. [Why the gate exists ->](/write/retries)

Retrying is not free and losim makes that visible. The retry interceptor sits
**outside** the recording one, so every attempt is a genuinely separate call,
with its own span, byte count, draw against loss, and look at whether the callee
is still alive. A design that retries is more expensive than one that does not,
and the bill will say so.

The less obvious fix is the better one: **notice sooner**. Your coordinator asked
every worker for its capacity at the start and never asked again. `cluster.serving
("Thumbnailer")` does not list dead machines — so a coordinator that re-checks
before dispatching each batch stops sending work to `w1` after the first failure,
instead of three times.
