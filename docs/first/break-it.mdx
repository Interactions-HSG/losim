A simulation where nothing goes wrong tests nothing worth testing. Add this to
`thumbs.yaml`:

```yaml simulations/thumbs.yaml
  workers:
    count: 4
    prefix: w
    instance: c5.large
    zone: [eu-central-1a, eu-central-1b]
    runs: { Thumbnailer: src/lab/Shrinker.java }
    overrides:
      w1:
        failures:
          # After the survey and in the middle of the work, so the coordinator
          # has to notice a node that is simply not there any more.
          - { kill: true, at: 900 refMs }
      w2:
        failures:
          # A noisy neighbour. Four times slower, and it does not die — which is
          # the failure most designs handle worst.
          - { degrade: 4, at: 1200 refMs }
```

Failures are written **inside the node they happen to**, so there is no name to aim
and no name to get wrong. Simulate it again.

## The failure, in order

```
thumbs.yaml  seed 7  completed in 3980 refMs
  1102 events, 340 spans, 68 series -> build/thumbs.json
```

Look at what the coordinator logged:

```
a batch did not come back: w1 did not answer (unreachable)
a batch did not come back: w1 did not answer (unreachable)
a batch did not come back: w1 did not answer (unreachable)
```

Three batches lost, and each one cost the coordinator **its full 2000 refMs
deadline** before it found out. The run went from 2416 refMs to 3980.

<Note>
That is the lesson, and it is not a bug in losim. A dead node, a cut link and a
lost packet are **one event from the caller**: nothing answers, and you find out by
running out of time. Modelling any of them as an immediate `UNAVAILABLE` would turn
the most instructive failure in distributed systems (you cannot tell a slow peer
from a gone one) into a tidy error code.
</Note>

## The four ways a message never arrives

<CodeGroup>
```yaml the node is gone
w1:
  failures:
    - { kill: true, at: 900 refMs }
```

```yaml the link is cut
w1:
  failures:
    - { partition: coordinator, at: 900 refMs }
    - { heal: coordinator, at: 2500 refMs }
```

```yaml the packet is dropped
network:
  loss: 0.02      # 2% of messages simply never arrive
```

```yaml this one rpc, on this one node
w1:
  runs:
    Thumbnailer:
      file: src/lab/Shrinker.java
      failures:
        Thumbnail:
          - { drop: true, per: 20 calls }
```
</CodeGroup>

All four produce the same thing at the call site: a `rpc_timeout` event and a
`DEADLINE_EXCEEDED` status, with `why` recording which it was — so the
trace can tell them apart even though your program could not.

## The whole catalogue of weather

Seven things that happen to a node, written in that node's `failures:`:

| | what it does |
|---|---|
| `kill: true` | the node stops answering. Add `restartAfter: 400 refMs` to bring it back. |
| `freeze: true` + `for: 300 refMs` | a stop-the-world pause. Calls **do not fail**; they wait, on the node's own threads, which is why a freeze is so much harder to diagnose than a crash. |
| `degrade: 4` | every declared cost on that node multiplied. A straggler rather than a casualty. |
| `spotReclaim: true` + `notice: 200 refMs` | the node tells you it is going, then goes. A design that ignores the warning deserves what happens. |
| `partition: coordinator` / `heal: coordinator` | the link between this node and that one, cut and restored. The only kind that names anything. |
| `restart: true` | back from the dead, with fresh service instances and an empty `local()`. |

And three that happen to **one rpc on one node**, written inside its `runs:` entry:
`status:`, `slow:` and `drop:`. That is how one bad replica is bad while its peers
are fine — the case every design handles worst.

## A standing rate, instead of a scripted afternoon

A failure at 900 refMs teaches the system to survive 900 refMs. A **rate** teaches
it to survive whenever — same block, `per:` instead of `at:`:

```yaml
  workers:
    count: 4
    prefix: w
    instance: c5.large
    runs: { Thumbnailer: src/lab/Shrinker.java }
    failures:
      - { kill: true,   per: 800 refMs }
      - { freeze: true, per: 400 refMs, for: 150 refMs }
```

Written on the pool, that is four nodes each drawing their own afternoon — not one
of the four failing every 800 refMs. The gaps are drawn exponentially from the seed,
so they vary the way real bad afternoons do.

<Note>
A rate has no end: each firing draws the next one, so it keeps happening for as long
as the run does. Nothing you write here can leave the system a quiet second half by
accident.
</Note>

**One seed is an anecdote.** A sweep is not a shell loop — losim is a library, so
write it in the language you are already in:

```java src/lab/Sweep.java
package lab;

import java.nio.file.Path;
import losim.runtime.Simulate;
import losim.sim.Loader;

/** One seed is an anecdote. Twenty is a result. */
public final class Sweep {

    public static void main(String[] args) throws Exception {
        var base = Loader.load(Path.of("thumbs.yaml"));
        int completed = 0;

        for (long seed = 1; seed <= 20; seed++) {
            var result = Simulate.of(base.withSeed(seed));
            if (result.completed()) completed++;
            else System.out.printf("seed %2d  %s%n", seed, result.failure());
        }
        System.out.printf("%d of 20 finished%n", completed);
    }
}
```

`Loader.load` reads the simulation you already wrote; `withSeed` returns a copy with
one thing changed; `Simulate.of` runs it in this JVM and hands back the result as an
object. Nothing is written to disk, nothing is parsed back, and a seed that failed prints
**why** rather than becoming an indistinguishable `false`.

<Tip>
`withSeed` has siblings — `withUnits`, `withWorkers`, `withoutWeather`, `withKTime`,
`withExpectedRun`. Any of them is an axis you can sweep the same way, which is how you
ask *"is this a bad seed or a bad design?"*

For a long sweep, hand in `Telemetry.Level.OFF`
(`Simulate.of(simulation, loader, Telemetry.Level.OFF)`) — a sweep asks whether the
run finished, not what happened inside it, and building a full trace twenty times is the
slow part.
</Tip>


## Now make it survive

The obvious fix is a shorter deadline plus a retry, and losim will stop you here.
That is the point:

```yaml
retries:
  - { method: Thumbnail, attempts: 3, backoff: 50 refMs, multiplier: 2 }
```

That one is allowed, because `Thumbnail` declared `NO_SIDE_EFFECTS` in the
`.proto`. Try it on a method that declared nothing and the run refuses at load,
naming the file and the line. [Why the gate exists ->](/write/retries)

Retrying is not free and losim makes that visible. The retry interceptor sits
**outside** the recording one, so every attempt is a genuinely separate call,
with its own span, byte count, draw against loss, and look at whether the callee
is still alive. A design that retries is more expensive than one that does not,
and the bill will say so.

The less obvious fix is the better one: **notice sooner**. Your coordinator asked
every worker for its capacity at the start and never asked again.
`peersServing("Thumbnailer")` does not list dead nodes — so a coordinator that
re-checks before dispatching each batch stops sending work to `w1` after the first failure,
instead of three times.
