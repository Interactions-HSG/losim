## The problem

losim runs on the machine's own threads. Opening a span, rendering an argument,
accounting a cost — each allocates and each takes wall clock, **on the very threads
whose allocation and duration are the measurement**.

The counters cannot tell losim's bytes from your program's. So losim has to.

<Warning>
And the distortion is not merely additive. The overhead is roughly constant **per
call** rather than proportional to the data in it, so in `demand = c + a·n^b` it lands
in `c` — and the probe grid runs at small `n`, where a fixed term is proportionally
largest.

Unmeasured, it inflates `c`, **drags the fitted exponent**, and the distortion is then
extrapolated to full scale.
</Warning>

## The mechanism

Every region of losim's own work is bracketed:

```java
long a0 = Meter.allocNow(), t0 = System.nanoTime();
…losim's work…
machine.charge(Meter.allocNow() - a0, System.nanoTime() - t0);
```

Charged to the machine's ledger **and** to the span it happened inside — so neither
the machine's reported allocation nor the handler's reported duration includes it.

```java
public long allocatedBytes() {
    return Math.max(0, rawAllocatedBytes() - losimBytes.get());
}
```

## Three details that make it exact

<AccordionGroup>
  <Accordion title="The bracket is not a helper taking a lambda" icon="code" defaultOpen>
    Constructing the lambda would allocate against the machine **before the first
    mark is even read**. So the two `Meter.allocNow()` calls are written out
    literally, everywhere.
  </Accordion>

  <Accordion title="Outside the bracket: calibrated and charged back" icon="magnifying-glass">
    A bracket reads the clock and the allocation counter twice, and the **first read
    of each pair is taken before there is anything to charge it to.**

    Measured once per JVM — around **70 ns** on a reference laptop — and charged back
    per metered stop. Without it, losim bills a machine *more* the more heavily its
    program is instrumented, which is exactly backwards.
  </Accordion>

  <Accordion title="The primitive overloads of `reveal` exist for this" icon="box">
    `reveal(String, Object)` boxes an `int` at the **call site** — before the bracket
    opens — so the box is charged to your program though it exists only because the
    parameter is an `Object`.

    Taking the primitive moves the boxing inside the bracket, where it belongs.

    At one call per handler this is invisible. At a thousand it bends the fitted
    memory exponent by **0.04**.
  </Accordion>
</AccordionGroup>

## The boundary losim cannot cross

In `reveal("keys", map.size())`, the `size()` is **your** work and is charged to your
program — correctly. Everything after the argument has been evaluated is losim's.

Similarly, `Losim.current().sleep(refMs)` charges the bookkeeping but leaves **the
wait itself outside the bracket**: it is the program's own declared duration, and
charging it to losim would subtract it straight back out of the span it exists to
lengthen.

## Only this machine's own threads can be subtracted back

<Note>
Only what landed on **this machine's own threads** can be taken back off it.

An async response is delivered on the channel's executor, which is not a machine at
all — its bytes were never counted against one, so subtracting them would credit the
machine for work it never did. The wall-clock charge still applies to the span; the
allocation charge does not.
</Note>

## The sampler is not on a machine's thread

Deliberately. What the sampler costs must not land on the counters it is reading, so
it runs on its own thread — `losim-sampler` — and is not part of any machine's pool.

## It is published, not hidden

```json
{ "name": "w0", "allocMb": 388.4, "losimMb": 0.44, "losimStops": 1284 }
```

<Note>
*"`allocMb` is the program's own"* is a **claim**, and a reader is entitled to see
the size of what was taken off it before believing it. So both the bytes and the
number of metered stops travel in the trace.
</Note>

## Does it actually work?

Measured at the extreme — a thousand `reveal` calls per handler, where losim charges
itself **54 MB** and meters **162,000 regions**:

| | moves by |
|---|---|
| the **unsubtracted** memory exponent | 0.026 — well outside its own noise |
| the **reported** exponent | 0.0004 — inside it |

Across four levels of instrumentation (telemetry off, no payloads, everything
rendered, and a thousand reveals per handler), the fitted allocation exponent moves by
0.0001 while losim's own charge goes from 0.31 MB to 54.19 MB.

<Warning>
**The extreme case is mandatory.** At one `reveal` per handler, a leak that halved an
exponent would be undetectable. This is the thing that regresses invisibly: every
number stays plausible and only the projection is wrong. The law your code is
projected by does not depend on how much you instrumented it.
</Warning>
