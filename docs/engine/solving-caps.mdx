title: "Solving the caps"
description: "How node capacity is projected from resource-specific laws."

---

The scale model preserves **ratio**, not size: demand over capacity, per
node, per resource.

```
cap = fixed + declared x (variable at run scale / variable at full scale)
```

## Resource-specific ratios

<Warning>
Memory follows what a node holds. Disk follows data volume. They grow at
**different rates**, so a uniform shrink factor would misrepresent at least one
resource.

The engine therefore solves each resource with its **own** ratio from that
resource's law.
</Warning>

## Keep the fixed term

A JVM's baseline heap does not shrink with the workload. Scaling the fixed
overhead below the JVM's requirement could cause an unrelated failure.

`fixed` is therefore added at full size, and only the **variable** part is scaled.

## Example

Suppose memory's law is

```
memoryMb = 0.06 + 0.00187 x distinctItems^1.013
```

and the run size is 8,000 units against a full scale of 40,000,000.

<Steps>
  <Step title="Project the variable at both scales">
    `distinctItems` is itself a law of units, so evaluate it at 8,000 and at
    40,000,000, then take the variable part of memory at each.
  </Step>
  <Step title="Take the ratio">
    `variablePart(8000) ÷ variablePart(40000000)`, clamped to at most 1.
  </Step>
  <Step title="Apply it to what the simulation declared">
    An `r5.large` declares 16,384 MB. Multiply by the ratio, add the fixed term back,
    floor at 1 MB.
  </Step>
</Steps>

The node keeps the same relation to its share of the scaled workload that the
full-size node has to its share of the full workload. An out-of-memory result in a
scaled run therefore remains a finding about the design.

## Choose a run size

The engine selects the largest rung on the probe ladder that is **feasible** in
both directions:

| | |
|---|---|
| large enough | the variable part is at least **ten times** the fixed overhead, or the fit is describing the overhead rather than the workload |
| small enough | the whole scaled system fits in **60%** of the host's max heap |

The selected size must be **actually measured**. A size beyond the ladder would
extrapolate beyond the measured range.

If no rung satisfies both, the engine names the resource and stops.

## Caps exposed to jobs

```java
at.count("lines");                       // the size the engine chose
Losim.current().here().memoryCapMb();    // the cap this node is under NOW
```

<Note>
`Spec` reports the **scaled** caps, not the instance type's full-scale caps. A job
that compares them can therefore place work the **same way at either scale**.

The placement decision from the scaled run remains meaningful at full scale.
</Note>

## Trace contents

The trace `meta` contains every solved cap, law, refusal, and the selected size.
Readers can recompute `projected = f(observed)` from those values.
