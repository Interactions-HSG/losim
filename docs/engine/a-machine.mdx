## The pool is the model

One `ThreadPoolExecutor`, with core and maximum both set to the instance's vCPU
count, using platform threads and prestarted.

That choice gives you three things:

<Steps>
  <Step title="Concurrency">
    Four calls into a two-vCPU machine queue.
  </Step>
  <Step title="Attribution">
    Every thread in the pool belongs to one machine, so `getThreadAllocatedBytes`
    over those thread ids is exact.
  </Step>
  <Step title="Boundary">
    Work on a thread outside the pool has no machine identity, is summed by nobody,
    and contends for nobody's cores.
  </Step>
</Steps>

<Warning>
`directExecutor()` must not be used. If it is, the caller's thread runs the handler
and the vCPU model disappears.

The threads must be platform threads, because `getThreadAllocatedBytes` returns `-1`
for a virtual one.
</Warning>

The pool is wrapped so that time spent waiting for a core stays separate from time
spent using one. Without the wrapper a queued call looks like a slow one.

## Memory: allocated versus held

| | measured by | tells you |
|---|---|---|
| `allocMb` | `getThreadAllocatedBytes`, exactly | how much churn |
| `memoryMb` | a **retained-heap walk** from the machine's roots | what would kill it |

Allocation counts garbage as well as survivors. The survivors decide an out-of-memory.

### The walk

The walk starts from the machine's own service instances, sums what is reachable, and
stops at the machine's edge.

- Application objects are reflected into. They live in the unnamed module, so their
  fields are accessible without opening anything.
- **JDK containers are modelled, not reflected into** — `java.util` is not open, and
  `setAccessible` on `HashMap.table` throws. Modelling their layout avoids
  `--add-opens`, which matters because losim has to run the same way in three places
  without launcher flags.

Object sizes assume compressed oops, which is on by default below a 32 GiB heap.

### A machine's boundary

| inside | outside |
|---|---|
| your fields, your collections | another machine, the cluster |
| the protobuf messages you hold — exactly your data | telemetry, spans, the clock, the network |
| | gRPC's transport, which everyone shares |
| | servers, channels, executors, threads |

That boundary is asserted by construction. losim's own structures sit outside every
machine's edge.

### The cadence, and the last walk

A walk costs about 0.06 microseconds per object, so a busy machine is walked every
eighth sampler tick. That is why `retainMb` steps rather than glides.

<Note>
There is also one final walk after the job ends. A machine that fills up between the
last walk and the end of the run has still filled up. Without this, an out-of-memory
could be missed in the closing moments.
</Note>

## Disk

Declared, not written. `wroteDisk(bytes)` adds to a counter and throws past the cap,
so the handler fails the way it would have failed for real.

## Faults, from the machine's side

| | what it does to the machine |
|---|---|
| kill | `alive = false`. Callers get `Dropped` calls that wait out their deadlines. |
| freeze | calls are **held at the door** on the machine's own threads, rechecked every couple of milliseconds so a machine thawed early is not still asleep |
| degrade | a multiplier on every declared cost |
| restart | a machine declared with `runs:` gets **fresh service instances**, so whatever it was holding is gone |

## Shutting one down

<Note>
`shutdownNow` is asynchronous. It asks the server to stop and returns, and the
in-process transport keeps the name registered until it actually has. One run per
JVM never notices, because the process exits.

The probe grid runs thirty clusters back to back in one JVM, all of them with a
machine called `w0`, and the thirty-first fails to bind a name the thirtieth has not
finished releasing. So the shutdown waits.
</Note>
