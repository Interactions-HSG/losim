Open the lab; the development servers start with the project.

<Steps>
  <Step title="Open the lab">
    In a Codespace or devcontainer, two servers start when you attach. Open
    `http://localhost:8000/`. In a Codespace, use the forwarded URL from the Ports
    panel.

    The manual is on port `3000`.

    <div id="run-something" />
    You get the list of systems in your project, and the runs you have made so far.
  </Step>

  <Step title="Run a system">
    Press the arrow beside a system. The lab reads its schema, compiles its Java,
    runs the simulation, and prices the result.

    A system with more than one simulation lists them all. `main.yaml` is the default
    configuration; other files represent different scenarios.
  </Step>

  <Step title="Run from the editor">
    At the root of the project is `RunExperiments.java`. Your editor puts a button
    above it:

    ```java RunExperiments.java
    Experiments.here()
            .run("main.yaml")
            .show();
    ```

    The same work is available as a file. Enable the runs you want to inspect. Add
    a `run` line for each run you want in the picker. The file can be reviewed and
    committed.

    `DisplayDocs.java` beside it does the same for the manual.

    [More ->](/first/simulate-it)
  </Step>

  <Step title="View a run">
    When the run finishes it appears in the picker. The viewer shows nodes, messages,
    and accruing cost.

    A run is in the picker because it is on disk under `build/results`.
  </Step>
</Steps>

<Note>
The manual is a separate process on `http://localhost:3000/`. This keeps it available
when the lab process fails.

The published site and the `.mdx` files under `docs/` also contain the manual.
</Note>

## Command line

The lab console provides common operations. Commands under `dissaly dev` are for losim
maintainers.

The console invokes the same launcher from the command line:

<Note>
`losim` is a command. `dissaly adopt` writes `./dissaly` into your project, like
`gradlew`. It builds the project and runs the simulator with the required classpath:

```bash
./dissaly simulate thumbs.yaml
```

In losim's own repository the same launcher is `bin/dissaly`, because the source
lives in `losim/` and a file cannot be a directory. Some pages here write
`bin/dissaly` for that reason.
</Note>

```bash
dissaly simulate thumbs.yaml --cp build/losim/classes --out build/results/thumbs.json
```

At a terminal this opens the viewer on the new run. It serves the trace directory, so
multiple simulations in that directory appear together.

<Tip>
`--no-view` writes the trace without opening the viewer. Redirected output also keeps
scripted sweeps non-interactive.

`--cp` points to compiled classes for the job and services named by the simulation.
Use a directory, not a jar, because the trust verifier reads class files from disk.
</Tip>

## Reading the report

A run reports something like this:

```text
thumbs.yaml  seed 7  completed in 3332 refMs
  874 events, 292 spans, 75 series -> build/results/thumbs.json
```

These fields are the important parts of the report:

| | |
|---|---|
| **`refMs`** | *reference milliseconds*, time in the simulated world. Host time and reference time differ by `k_time`. |
| **events / spans / series** | the three telemetry channels. Events are moments, spans are intervals that carry a parent, series are dense numbers on a fixed cadence. |
| the trace path | the file that matters. Everything downstream reads it. |

The exit code matters when scripting `dissaly simulate`; the button reports the failed
step for you:

| code | meaning |
|---|---|
| `0` | `Job.Run` completed |
| `1` | the job failed or exceeded its allowed time |
| `2` | configuration error: an unknown key, an unknown instance type, or a duration with no unit. The simulation did not run. |
| `3` | something went wrong inside losim |
