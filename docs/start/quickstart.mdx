Open the lab. The development servers start with it.

<Steps>
  <Step title="Open the lab">
    In a Codespace or the devcontainer, two servers start when you attach. Open
    `http://localhost:8000/`. In a Codespace, use the forwarded URL from the Ports
    panel instead of `localhost`, and VS Code opens a preview on it.

    The manual is on port `3000`. If you have to start from a terminal, something
    is wrong and the course wants to hear about it.

    <div id="run-something" />
    You get the list of systems in your project, and the runs you have made so far.
  </Step>

  <Step title="Run a system">
    Press the arrow beside a system. That reads its schema, compiles its Java, runs
    it in the world its scenario describes, and prices what happened.

    A system with more than one scenario lists them all. `main.yaml` is the ordinary
    world, and a variant beside it is a second question.
  </Step>

  <Step title="Run from the editor">
    At the root of the project is `RunExperiments.java`. Your editor puts a button
    above it:

    ```java RunExperiments.java
    Experiments.here()
            .run("main.yaml")
            .show();
    ```

    The same work is available as a file. Comment lines in and out to choose what
    you are looking at. Two `run` lines are two runs side by side in the picker.
    Unlike a click, this file is diffable, commentable, and committable.

    `DisplayDocs.java` beside it does the same for the manual.

    [More ->](/first/run-it)
  </Step>

  <Step title="Watch it">
    When the run finishes it appears in the picker, and the viewer shows the
    machines, the messages between them, and the money accruing while it goes.

    A run is in the picker because it is on disk under `build/runs`.
  </Step>
</Steps>

<Note>
The manual is a separate process on `http://localhost:3000/`, started the same way.
That separation is deliberate. This is where you look when something will not start,
so it should not be served by the thing that will not start.

The published site and the `.mdx` files under `docs/` are the other two places in.
</Note>

## The command line

You never need it, and no page in this manual asks you to. The lab console has a
button for everything below. Everything under `losim dev` is a maintainer command
for whoever works on losim itself.

It is there, though, and it is what the button calls:

<Note>
`losim` is a command. `losim adopt` writes `./losim` into your project, the same
way `gradlew` does. It runs the build and then the simulator, so there is no
separate build step and no classpath to get right:

```bash
./losim run thumbs.yaml
```

In losim's own repository the same launcher is `bin/losim`, because the source
lives in `losim/` and a file cannot be a directory. Some pages here write
`bin/losim` for that reason.
</Note>

```bash
losim run thumbs.yaml --cp build/losim/classes --out build/runs/thumbs.json
```

At a terminal this opens the viewer on what it just ran and keeps it open. It
serves the trace's own directory, so several scenarios written into one directory
are all in the picker together.

<Tip>
`--no-view` writes the trace and stops. A run whose output is redirected does not
open anything either, so a scripted sweep stays a scripted sweep.

`--cp` is where your compiled classes are, meaning the job and the services the
scenario names. Point it at a directory, not a jar, because the trust verifier reads
class files off disk.
</Tip>

## Reading the report

A run reports something like this:

```text
thumbs.yaml  seed 7  completed in 3332 refMs
  874 events, 292 spans, 75 series -> build/runs/thumbs.json
```

Three things are worth understanding straight away:

| | |
|---|---|
| **`refMs`** | *reference milliseconds* — time in the simulated world, not your afternoon. The two differ by `k_time`. |
| **events / spans / series** | the three telemetry channels. Events are moments, spans are intervals that carry a parent, series are dense numbers on a fixed cadence. |
| the trace path | the file that matters. Everything downstream reads it. |

The exit code matters only if you are scripting `losim run`; the button reads it
for you and says which step failed:

| code | meaning |
|---|---|
| `0` | the job completed |
| `1` | the job did not complete — it threw, or outstayed its welcome |
| `2` | the scenario is wrong: an unknown key, an unknown instance type, a duration with no unit. Nothing ran. |
| `3` | something went wrong inside losim |
