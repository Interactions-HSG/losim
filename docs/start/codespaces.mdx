## Open the project

<Tabs>
  <Tab title="GitHub Codespaces">
    From the repository page: **Code -> Codespaces -> Create codespace**.

    The container builds and runs `./gradlew jar`; when the terminal appears,
    `build/losim.jar` already exists.
  </Tab>
  <Tab title="VS Code, locally">
    With Docker running and the **Dev Containers** extension installed, open the
    repository and accept **Reopen in Container**.

    It uses the same image and commands as a Codespace. CI checks this setup.
  </Tab>
</Tabs>

## The container's contents

| | |
|---|---|
| **Java 25** | from the base image `mcr.microsoft.com/devcontainers/java:25-bookworm`. losim compiles at `--release 21`, so anything from 21 up works. |
| **The vendored toolchain** | gRPC 1.83.1, protobuf 4.36.0 and `protoc` for two platforms, committed under `vendor/`. Nothing is fetched to compile or to run. |
| **Gradle 9.2.0** | from the committed `./gradlew`, not from the image. The image carried one until it was rebuilt without it, and a build that depends on what the image ships this month is a build that stops working without anybody touching it. The wrapper fetches that one version on create and checks its sha256. |
| **Node 22** | only for developing the viewer. Neither losim nor this manual needs it. |
| **Port 8000** | **the lab**, including the viewer, runs, and system controls. |
| **Port 3000** | **the manual**, running as a separate process. |

Both ports are forwarded automatically. In a Codespace, VS Code shows the URL in the
**Ports** panel.

<Note>
**The lab and manual run as separate processes.** The manual remains available when
the lab fails, and your code cannot affect the manual process.

Read the manual through this port, the published site, or the `.mdx` files under
`docs/`.
</Note>

## Container commands

```bash
./gradlew jar                                       # on create:  the simulator
bin/losim serve --detach && bin/losim serve docs --detach   # on attach: both ports
```

`--detach` checks the port before starting a process, so re-attaching does not create
duplicate servers.

<Note>
The manual is rendered by the JDK in the image. The setup does not download a CLI
through npm.
</Note>


## Commands

<CodeGroup>
```bash losim
bin/losim dev test        # losim's own acceptance criteria
bin/losim dev suite       # the reference suite: gRPC systems, end to end
bin/losim dev docs check  # that this manual gives no assignment away
```

Each command builds the simulator first. `bin/losim` runs `./gradlew jar` and then the
JVM command.

```bash your work
./losim simulate  mine.yaml --cp build/losim/classes --out build/results/mine.json
./losim bill build/results/mine.json
./losim compare build/results/a.json build/results/b.json
```



```bash the servers
# started for you on attach; this is what runs
./losim serve         # the lab    -> :8000
./losim serve docs    # the manual -> :3000

```


</CodeGroup>

<Note>
Node 22 is in the image only for previewing the manual and **developing** the viewer.
losim and run inspection use the committed viewer export and the JDK.

</Note>

These commands are also available as VS Code tasks: **Terminal -> Run Task**.

## The toolchain is vendored on purpose

The same simulation on different hosts should use the *same simulator*.
If the gRPC version drifted, serialized byte counts could change with the host.

CI checks this by running the reference suite on a plain runner and **inside the
Codespace image**, then comparing the traces with `losim compare`. Structure and
attribution must agree, while measurements may differ because hosts are different.

<Warning>
**A Codespace can change timing noise.** The scale engine measures that noise, so it
may refuse to project a timeline in a Codespace that projected on a laptop. See
[refusal handling](/simulate/refusals).
</Warning>
