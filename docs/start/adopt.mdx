You have a gRPC Java system that works — a `.proto`, handlers, a server that binds
a port, a client that dials one. losim runs **those handlers**, unchanged, on many
simulated nodes over a simulated network, and tells you what the design cost.

```bash
curl -sSLo losim.jar https://github.com/Interactions-HSG/losim/releases/latest/download/losim.jar
java -jar losim.jar adopt .
```

<Note>
Commit first. It moves files with `git mv` so your history follows them, and it
refuses a dirty tree unless you pass `--dirty`.
</Note>

## What it does, and what it will not

| it does | it does not |
|---|---|
| `git mv src/main/proto -> proto/`, `src/main/java -> src/` | rename a package or rewrite an import |
| write `build.gradle.kts`, `./losim`, `AGENTS.md`, a first simulation, `.gitignore` | overwrite a file it did not author |
| move `build.gradle` aside to `build.gradle.bak` | delete a `.java` |
| print every Java edit still needed, with a line number | make one |

**It never writes Java**, and that is not squeamishness. Both edits the obvious
version of this command would make are unsafe in the shape a real project has: the
handler is usually a nested class inside the server bootstrap, so extracting it is
a refactoring engine and a bad extraction silently drops a field initialiser — and
turning a client into a `losim.Job` is a judgement about which of its lines are the
design and which are the transport, which is the thing this course is about.

So it hands that half to you, in `AGENTS.md`, with the findings it just made. If
you work with a coding agent, that file is written for it.

## The two edits

### 1. The handler comes out of the bootstrap

```java
public class HelloWorldServer {                     // ← all of this goes
  public static void main(String[] args) { … }
  static class GreeterImpl extends GreeterGrpc.GreeterImplBase {   // ← this stays
    @Override public void sayHello(HelloRequest req, StreamObserver<HelloReply> out) { … }
  }
}
```

becomes a file of its own, and the rest is deleted:

```java
public final class GreeterImpl extends GreeterGrpc.GreeterImplBase {
    @Override public void sayHello(HelloRequest req, StreamObserver<HelloReply> out) { … }
}
```

<Warning>
**Leaving it nested is not enough.** The trust verifier walks a nested class
together with the class enclosing it, so the bootstrap's own server, its channel
and its statics are read as the service's — and every figure that node reports
comes back marked. [Trust rules ->](/ref/trust-rules)
</Warning>

Top-level, with a no-argument constructor, and in a file named after it: `runs:`
names the `.java` file, losim reads the class out of it, and builds a fresh one each
time a node restarts.

### 2. The client is `losim.Job` in disguise

The client is the thing that drives calls, which is what `losim.Job` is for.

<CodeGroup>
```java before
ManagedChannel channel = Grpc.newChannelBuilder("localhost:50051",
        InsecureChannelCredentials.create()).build();
try {
    var stub = GreeterGrpc.newBlockingStub(channel);
    var reply = stub.sayHello(HelloRequest.newBuilder().setName("world").build());
    logger.info("Greeting: " + reply.getMessage());
} finally {
    channel.shutdownNow().awaitTermination(5, TimeUnit.SECONDS);
}
```

```java after
public final class Greeting extends JobGrpc.JobImplBase {

    @Override public void load(Input in, StreamObserver<Workload> out) {
        out.onNext(Workload.newBuilder().setCount(in.getCount()).build());
        out.onCompleted();
    }

    @Override public void run(Workload work, StreamObserver<Result> out) {
        var here = Losim.current();
        String peer = here.peersServing("Greeter").get(0);
        var stub = GreeterGrpc.newBlockingStub(here.channelTo(peer));
        var reply = stub.sayHello(HelloRequest.newBuilder().setName("world").build());
        out.onNext(Result.newBuilder().putAnswer("greeting", reply.getMessage()).build());
        out.onCompleted();
    }
}
```
</CodeGroup>

Three things go: the channel builder, the host and port, and `shutdownNow`. **A peer
is found by what it serves, never by an address.**
[Calling peers ->](/write/calling-peers)

`Load` has nothing to build here, so it hands back the count it was given. A system
with a real workload does its reading there instead, off the clock.
[losim.Job ->](/ref/losim-proto)

## Then fill in what a call costs

`adopt` writes a simulation with every rpc at `fixed: 0 refMs`. Leaving it there is
the step most often skipped, and skipping it makes every number meaningless: every
call is instant, so there is no queueing, no contention and no critical path, and
the run finishes in almost no time for almost no money.

```yaml
simulatedDuration:
  src/main/java/io/grpc/examples/helloworld/GreeterImpl.java:
    SayHello: { fixed: 3 refMs }
```

Nothing measures this for you and nothing can — at the size a laptop can hold your
handler *is* instant, because the workload is shrunk and the host's CPU is not.
[Why it is declared ->](/write/declaring-time)

## What you end up with

```
proto/            your schema, moved
src/              your Java, moved — and otherwise untouched
gen/              what protoc writes, beside the schema. Generated; gitignored
simulations/        1-one-call.yaml, and every one you write after it
build.gradle.kts  losim, protoc, and the toolchain task
losim             the launcher: `./losim build`, `./losim simulate`, `./losim serve`
AGENTS.md         what was left, in the three classes below
build.gradle.bak  what your build used to be
```

```bash
./losim check     what is still between this and a run
./losim build     generate from the schema and compile
./losim simulate simulations/1-one-call.yaml
./losim serve     the lab, on :8000
```

## The three classes of finding

`adopt` and `check` print the same list, and it is in three parts because the
three are not the same kind of problem.

<AccordionGroup>
  <Accordion title="Refused — it will not run" icon="ban">
    The loader says so, with a line number, before anything starts. A streaming
    rpc, a service that is not a protoc `ImplBase`, a `simulatedDuration:` key naming a method
    nothing serves.
  </Accordion>
  <Accordion title="Untrustworthy — it runs, and a number is wrong" icon="triangle-exclamation" defaultOpen>
    The verifier says so, per node, in the trace. Your own channel, your own
    thread, a real sleep, the real clock, a real file. These are the dangerous
    ones: the run completes and the number beside the marker is not what it says
    it is. [The rules ->](/ref/trust-rules)
  </Accordion>
  <Accordion title="Dead — it runs, does nothing, and nothing else will say so" icon="ghost">
    A `main` and its argv, a shutdown hook, `awaitTermination`, credentials, a
    fixed thread pool, a logger, `grpc-netty-shaded`, the `application` plugin.

    None of it is a wrong number, so the verifier is right to be silent — which is
    exactly why this list exists. `main` is the one worth reading twice: with no
    simulation named, losim runs the first class it finds with one, so a leftover
    `main` can be launched by pressing the arrow and will try to bind a port.
  </Accordion>
</AccordionGroup>

## What it refuses to adopt

A `pom.xml`, a multi-module `settings.gradle`, a directory with no schema and no
service in it, and a dirty tree without `--dirty`.
