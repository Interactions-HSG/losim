A trace is a few thousand JSON objects. The viewer is how you look at one — and it
opens **a raw `losim run` trace**, with no baking step in between, because the case it
exists for is a student pointing it at their own run.

## Try it now

It is already open. In a Codespace or the devcontainer the lab server started when you
attached, on **http://localhost:8000/**, and every run under `build/runs` is in the
picker — a run is listed because it is on disk, which is the only fact that cannot go
stale.

If you would rather say which runs to look at, `show()` opens the viewer on exactly
the ones you just made:

```java RunExperiments.java
Experiments.here()
        .run("main.yaml")
        .show();
```

<Note>
**Every example in this manual makes its own trace.** There is no shared set of
prepared runs you are expected to have, and nothing here depends on one existing —
each page that shows you a picture also shows you the run that produced it.
</Note>

<Note>
**You need no Node and no install.** The page is committed as a static export and
served by the JDK that is already there, so it is the same in the devcontainer, on a
laptop and in a Codespace, with no setup step and no first-run download.

`npm` belongs to whoever *changes* the viewer. [Developing it ->](/viewer/developing)
</Note>

## The clock is in reference milliseconds

<Note>
The scrubber reads the clock **the scenario was written in**, not the compressed one
the host actually ran at — whatever `k_time` happened to be. That is the only reading
a student can carry back to the YAML they wrote.
</Note>

<Warning>
**The playhead does not move at a constant rate, and `1x` is not one simulated second
per real second.** A call that took three refMs would be on screen for three
*thousandths* of a second — and the short, fast control messages are exactly the ones
carrying the payloads worth reading, so the interesting things were the invisible
ones.

The clock therefore **slows down wherever something quick is happening**, so that
every leg of every message and every stretch of work is on screen for at least a
second. The **hold** button cycles `1s -> 0.5s -> 0.25s -> off`.
</Warning>

Nothing but the pace changes, and that is what makes it honest rather than a
distortion:

| | |
|---|---|
| **monotone** | trace time never goes backwards, so nothing is reordered and nothing overlaps that did not overlap |
| **read at the true instant** | every number on screen is taken from the trace at the trace time the playhead is at — a machine's memory at 400 refMs is what it was at 400 refMs |
| **the scrubber is still refMs** | the axis is unchanged; only the speed along it varies |

**So the film is longer than the run, often much longer** — a five-second run is
commonly a fifty-second film, and a run full of short messages is longer still. That
is the price of the guarantee, and the clock says the number: beside the elapsed time
it prints how long the film itself runs.

Turn `hold` down, or off, when you want the run back at its own speed.

### `fit`, and the one place the guarantee lapses

`fit` plays **the whole film in thirty seconds** — the film, not the run. The pacing is
kept, so the quick parts still get far more than their share of the time; they are
simply squeezed along with everything else.

Which means the one-second floor is a **`1x` promise**. At `fit`, each moment gets
`30s ÷ the film's length`:

| | run | film | each moment at `fit` |
|---|---|---|---|
| a small run | 5.2s | 57.0s | ~0.53s |
| a run full of failures | 8.9s | 165.0s | ~0.18s |

So `fit` is for getting the shape of a run you have already understood, and `1x` is for
reading one. `hold` decides the **shape** of the film; `fit` decides **how long you
spend watching it**. Pressing any numbered rate clears `fit`.

<Tip>
Turn `hold` **off** and `fit` becomes what you would first assume it was: the whole run
in thirty seconds, at a constant rate, short things flashing past.
</Tip>



<Tip>
**Do not judge relative duration from the film** — that is what the pacing trades
away. The film answers *what is happening*; the
[waterfall](/viewer/views#spans) answers *how long did it take*, and it draws

a plain linear axis for exactly that reason. It is deliberately not paced.
</Tip>


## Status

The console has a rail of pages. **Runs** is the gallery you land on, **Scenarios**
lists every scenario in the lab, writes a new one from the palette or edits one
that already exists, and runs it — pressing ▶ moves you straight to Runs, where
the trace lands when it is ready. **Overview**, **Film**, **Usage** and **Cost**
all read a single trace, and all four share one clock, so dragging the bar moves
every one of them to the same instant. **Spans** and **Topology** are sub-views
inside Film. [What each one shows ->](/viewer/views)

Two runs can also be watched **side by side on one clock**: pick a second from
`compare with…` and both films run against the same instant, with a line underneath
saying which is ahead on money and by how much.
[How that works ->](/viewer/views#two-runs-on-one-clock)


## A film, not a video

An earlier Python prototype rendered a run as a **video file**, and it was measured
and dropped: a rendered video cannot be hovered, scrubbed or interrogated, and all the
views that matter are interrogation views.

What replaced it keeps the playback and adds everything a video cannot do. Every
element is a pure function of the frame it is given — no state, no imperative drawing
— which is what makes **scrubbing, playing and recording one code path**.

Four of its modules survive as the **reference the port is checked against** — glyph
path by glyph path, layout by layout. The renderer that produced the video is not one
of them. [How that is checked ->](/viewer/developing)

<Note>
So the MP4 the recorder produces is literally the film you watched. And because the
clock is an *input* to the encoder rather than a consequence of it, a slow laptop
produces a byte-for-byte identically-timed file to a fast one; it just takes longer to
make.
</Note>

## The stack

| | |
|---|---|
| **Next 16** + **React 19** | `output: 'export'` — a static site, no server |
| **d3 7** | scales, timers, geometry |
| **mediabunny** | MP4 export through WebCodecs |

Considered and rejected: elkjs, Radix, framer-motion, react-virtual. Fifteen
dependencies would mean a viewer that stops building in two years. Nothing is fetched
at runtime, so nothing depends on the network being there.
