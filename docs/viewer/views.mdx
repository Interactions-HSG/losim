Every view reads the same `(trace, t)` and shares one selection. Switching views
changes the question while preserving the underlying state.

The table maps viewer pages to their drawings. **The Film page contains the film**;
Topology, Spans, and the Ledger also appear in Overview or Cost.

| the question | the drawing | where it is |
|---|---|---|
| what is true *right now*? | **Film** | the Film page |
| what is the *shape* of this system? | **Topology** | Overview, section 1 |
| why did it take that long, and who was waiting on whom? | **Spans** | Overview, section 2 |
| what did it cost, while it was being spent? | **Ledger** | the Cost page, Overview section 5, and over the film with `ledger=1` |

The top rail contains the pages. **Runs** is the gallery, and **Simulations** is where
labs are written, edited, and run. **Overview**, **Film**, **Usage**, and **Cost** read
one trace and share its clock.

### Overview reads in order

Overview uses numbered sections. Every section is drawn at the current clock
position, so scrubbing moves them together.

| | section question | answer |
|---|---|---|
| 1 | what is this system made of? | the **Topology** map |
| 2 | what did it actually do? | the **Spans** call tree |
| 3 | how hard is each node working? | the system, at this instant |
| 4 | what has gone wrong? | every accident, each one a button that seeks to it |
| 5 | what did it cost? | the four buckets, as they arrive |

## Film view

The system at an instant. Zones are bands, and roles are columns derived from the
trace.

<Columns cols={2}>
  <Card title="Node size reflects resources" icon="ruler-combined">
    More memory makes a node wider; more cores make it taller. A `c5.4xlarge` is
    visibly larger than an `a1.medium`.
  </Card>
  <Card title="Remaining capacity" icon="battery-half">
    The panel shows remaining capacity, not only usage. Remaining memory determines
    how close the node is to its cap.
  </Card>
</Columns>

Messages in flight carry a digest of their payload. `--telemetry FULL` also preserves
the payload needed for inspection.

**Filters** by zone, role, and task dim nodes while keeping the layout stable.

<Note>
**The picture shows only what is currently true.** A completed call is *absent* at
later times. Each element is a function of the current instant.
</Note>

### Colour meanings

| | |
|---|---|
| a node's fill | what it holds |
| **amber** | approaching its cap, or warned it is going |
| **red** | past it, or gone |
| **blue-grey** | frozen: still there, answering nothing |
| a task's hue | kept for the whole run, so one piece of work is followable |

Red is an alert color, not a system state. The film follows the light or dark theme
for its **ground**; the meanings above do not change.

## Spans

*Section 2 of Overview.*

The distributed call stack. The views share one tree, time axis, and selection.
Hovering a row highlights the call in the film and panel; clicking seeks.

<Warning>
**Spans uses a linear time axis.** The film slows down for quick events; Spans does
not.

**The film shows activity; the waterfall shows duration.** Use Spans to compare call
durations.
</Warning>


<Note>
Every span carries a parent, and losim propagates it **across the RPC boundary in a
metadata header**. The result is a distributed call stack rather than separate
per-node timelines.

```
phase    thumbnails                 master   1991 → 3581
  rpc    Thumbnailer.Thumbnail      master   2040 → 3575     to w2
    handler Thumbnailer.Thumbnail   w2            2042 → 3554
      rpc  Registry.Announce        w2            2069 → 2140     to desk
        handler Registry.Announce   desk          2072 → 2116
```

The tree shows nested work across four nodes. It makes remote fan-out and caller
waiting visible.
</Note>

### Bar segments

```
Thumbnail → w2   ├─┤███████████████████████████████├──┤
                 out   queue      working          back
```

Each segment is **measured** by subtraction, so the segments tile the bar. `netRefMs`
gives wire time; the gap before the handler opens is queue time on a full node.

### Span measures

<Columns cols={2}>
  <Card title="Self time" icon="hourglass-half">
    A span's duration minus its children's: the work that node performed. The
    remainder was spent waiting. It is drawn lighter inside the bar.

    Children are a **union, not a sum**. Four concurrent child calls overlap, so
    adding them would overstate the parent's waiting time.
  </Card>
  <Card title="The critical path" icon="route">
    At each level, the child that finished last. It contributes to the makespan and
    is outlined in the waterfall.
  </Card>
</Columns>

### Span sub-views

| | |
|---|---|
| **Waterfall** | causality and the primary view. Tree order is indented by depth; subtrees collapse. |
| **Swimlanes** | place: a lane per node, grouped by zone, with arrows where work moved between them. |
| **Rollup** | what the job is made of: self time by method, node, zone or task. |

### Span filters

Filters include node, method, failed-only, critical-path-only, and **slower than**.

## Topology

*Section 1 of Overview.*

Topology shows caller relationships over the whole run. Film shows the current instant,
while Topology preserves the system's structural shape.

<Columns cols={2}>
  <Card title="The same layout as the film" icon="map-pin">
    The viewer uses the same derived layout as Film, so `w0` stays in the same place
    in both views.
  </Card>
  <Card title="Edges weighted by bytes" icon="weight-hanging">
Edge weight comes from the destination of the system's **data**, not call count. A
    master asking forty nodes a one-word question has forty thin edges; the
    one call that moved a megabyte is the fat one. Cross-zone edges are tinted because
    the ledger charges for them.
  </Card>
</Columns>

The clock still runs, so edges **thicken as their calls occur**. Scrubbing shows the
shape as it develops.

## Ledger

<div id="the-ledger" />

*The Cost page gives the ledger more room for each line, the buckets at the current
time, and a second run. The same accrual is available as a panel over the film with
`ledger=1`.*

The buckets accrue **while the film plays**:

| | |
|---|---|
| `capacity` | flat from the first frame: you bought a minute of every node before a single call was made |
| `build` | creeps |
| `consumption` | follows the work. **Algorithm changes affect this bucket.** |
| `incidents` | steps, at the instants things broke |

`losim bill` reports the final cost. The ledger shows the incidents bucket filling as
the run proceeds.

### Node cost attribution

The viewer moves its lines to the top with the reason in words. Other lines dim, and
the node's slice appears inside each bucket's bar. Attribution identifies who is
responsible for each line:

| | |
|---|---|
| **its own** | a capacity line names one node and belongs to it entirely |
| **its share** | a system total split by a quantity the trace already holds, such as cross-zone egress by the bytes that node sent |
| **the worst node's** | storage belongs wholly to it, because that is what the bill charges for |
| **the event's node** | incidents go to the node the event names |
| **nobody's** | the late-finish penalty belongs to the *job*. Spreading it over nine nodes would invent a claim nothing supports, so it shows as a dash |

<Warning>
**Prices come from the CLI.** The viewer distributes each amount over time using the
rate table, and the closing total matches `losim bill` **to the rappen**.

No bill beside the trace means no cost is shown.
</Warning>

## Driving the viewer

### Keys

| | |
|---|---|
| `Space` | play / pause |
| `Right Arrow` `Left Arrow` | one frame; **Shift** for ten |
| `]` `[` | jump to the next / previous **event** |
| `Esc` | unpin the node panel |

### Playback speed

| | |
|---|---|
| `1x` | the run at its own pace, with the quick parts held long enough to read. **This is the only speed where the one-second floor holds.** |
| `2x`, `4x`, etc. | the same shape, faster. Pressing one clears `fit`. |
| `fit` | the whole **film** in thirty seconds. The pacing is kept but squeezed, so each moment gets `30s / the film's length`, well under a second on a long film. |
| `hold` | cycles `1s -> 0.5s -> 0.25s -> off`, and decides the shape of the film rather than how fast you watch it. Off means no pacing at all. |

`hold` and `fit` compose: one sets the pacing, and the other sets total viewing time.
[Why the clock is paced at all ->](/viewer/index#the-clock-is-in-reference-milliseconds)

### The message panel


Pause, then **hover a message in flight**: its full payload, its size in bytes, how
long it spent on the wire, and how it ended. **Click to pin it** so a thousand-entry
payload can be read while it scrolls.

A trace that kept only a bounded sample of a large payload says so, and says the true
count, so a truncated list is never mistaken for a short one.

<Tip>
This is the reason the film is paced. A control message that took three refMs is on
screen long enough to hover precisely because the clock slows down for it.
</Tip>

### The node panel


**Hovering opens the node panel.** **Click to pin** it, and it keeps updating
while the film plays, so you can see a node fill up. Pinning **docks it beside the
film** and the picture re-fits into the remaining space; hover still overlays without
moving the picture under the cursor.

The panel reports the node's identity, contents relative to its caps, computation on
the **whole** payload, served work, events, and cost. The sparklines cover the whole
run with the current instant marked, so each reading has surrounding context.

### URL parameters

| parameter | |
|---|---|
| `run=<name>` | which trace |
| `vs=<name>` | a second run, on the same clock |
| `t=<refMs>` | the instant |

| `view=<page>` | which page of the console: `runs`, `simulations`, `overview`, `film`, `usage`, `cost` |
| `sv=waterfall \| swimlanes \| rollup` | which sub-view of Spans, on Overview |
| `m=<node>` | pins the panel on it |
| `ledger=1` | opens the ledger |
| `fail=1` | failed spans only |
| `method=<text>` | filter by method |

```
http://localhost:8000/?run=mine&t=2400&view=overview&sv=waterfall&fail=1
```

*"Look at the failures in `mine` at 2,400"* can be encoded in one link.

## Recording

The viewer records the film as MP4 or WebM, depending on the browser. Playback and
recording use the same code path; only the clock driver differs.

<Note>
The clock is an **input** to the encoder, so a slow laptop produces a file of the same
length and rate as a fast one. Recording the live canvas through `MediaRecorder` can
produce a shorter, less consistent video on a throttled node.
</Note>

Export after inspecting the trace. An exported video cannot be hovered.

## Comparing runs on one clock

Pick a second run from **`compare with...`**, beside the run picker. Both films play at
once, against the same instant.

<Note>
**Both films use one clock in absolute refMs.** The clock runs until the longer run
finishes. The shorter run ends at its own finish time and is captioned `finished at ...`.
</Note>

Each film gets half the stage and is **re-arranged for that space**. When both traces
have bills, a line below them shows each cost and the difference.

<Warning>
**The comparison applies only to Film.** Spans, Topology, and the node panel show the
run you picked first, on the left. Hovering works on the left film; the `vs` film is
display-only.

The **task** filter applies to both. The zone and role filters dim only the left.
</Warning>

The pairing is in the URL as `vs=<name>`, so a comparison is a link like any other
moment.

<Tip>
The comparison worth making is almost always **one variable changed**. Run a simulation,
edit exactly one line of the YAML, run it again into a second file, and put the two
up together, so the difference on the stage is attributable to that line.
</Tip>
