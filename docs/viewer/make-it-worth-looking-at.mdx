The viewer can only draw what the trace contains. All of these are things you were
going to want anyway, and each one has a specific consequence you can point at.

<Steps>
  <Step title="Make each stage an rpc — they become the shape of the picture">
    ```java
    var stub = ThumbnailerGrpc.newFutureStub(here.channelTo(worker));
    ```

    Every call is a labelled span, drawn on the node that served it and hanging
    beneath the call that made it. *"Which stage was this?"* is the question a viewer
    asks before any other, and the answer is which rpc was in flight.

    A `Run` that does everything itself is one undifferentiated root span and you
    count pixels. A `Run` that hands work to three services is a story you can seek
    around — and in the [Spans view](/viewer/views#spans) that is the tree.
  </Step>

  <Step title="Reveal real numbers — they fill the node panel">
    ```java
    Losim.current().reveal("frames", request.getFramesCount());
    Losim.current().reveal("jpegKb", bytes / 1024.0);
    ```

    This is what puts **real numbers on a node** instead of "it was busy". Pin the
    node and watch them move — pinning docks the panel beside the film, so the
    picture stays visible while you read.

    Use the primitive overloads — the `Object` one boxes at the call site, and at a
    thousand calls per handler that bends the fitted memory exponent.
  </Step>

  <Step title="Declare what your handlers cost — or the film has no duration">
    ```yaml
    simulatedDuration:
      src/lab/Shrinker.java:
        Thumbnail: { fixed: 3 refMs, perUnit: 240000 refNs }
    ```

    Without it every handler is instant, every message crosses in a single frame, and
    there is no queueing, no contention and no critical path to watch. An unpriced
    rpc takes no time, deliberately — so an unpriced system is a blur.

    It goes in the **simulation**, under the same path `runs:` names. If you have
    seen a `@Takes` annotation or a `takes:` block in older notes, neither is what
    loads any more.
  </Step>

  <Step title="Declare how many units each call processed">
    ```java
    Losim.current().units(request.getFramesCount());
    ```

    It lands on the span, so a handler's duration reads against the work it actually
    did rather than against nothing — and it is on the span in the
    [Spans view](/viewer/views#spans), beside the duration it explains.
  </Step>

  <Step title="Account for disk — it is the only way the Ledger gets a storage line">
    ```java
    Losim.current().wroteDisk(bytes);
    ```

    It throws when the cap is exceeded, because that is the disk model rather than
    bookkeeping, and a `disk_full` puts a red marker on the scrubber at the instant it
    happened.
  </Step>

  <Step title="Put the trace where the viewer looks">
    ```bash
    --out build/results/mine.json
    ```

    A run is priced as part of making it, so the Ledger has money in it straight away.

    A trace dragged onto the page has no bill beside it and shows none.
  </Step>
</Steps>

## And two that change the picture more than anything else

<Columns cols={2}>
  <Card title="Do the reading in Load" icon="inbox">
    ```java
    @Override public void load(Input in, StreamObserver<Workload> out) { … }
    ```
    `Load` runs off the clock, so building the workload costs nobody anything and
    appears nowhere. Do it in `Run` instead and the coordinator's root span opens
    with a long stretch of one node working alone — an accurate picture of a design
    that is spending its run reading a file.
  </Card>
  <Card title="Dispatch asynchronously" icon="arrows-split-up-and-left">
    ```java
    ThumbnailerGrpc.newFutureStub(channel)
    ```
    With a blocking stub in the dispatch loop, exactly one node is ever lit at a
    time and the rest sit idle for the whole run. It is the single most obvious thing
    the film shows you, and the single most common reason a first system turns out to
    be one node with extra steps.
  </Card>
</Columns>

## Telemetry level

```bash
--telemetry FULL          # the default, and what you want for looking
```

`FULL` records every call's **real argument and real result**. That is by a distance
the most expensive part of recording — and it is what the film draws on a message in
flight, and what the pinned panel shows in full rather than as a digest.

Use `NO_PAYLOAD` for a run you are going to *measure*, and `FULL` for a run you are
going to *watch*.

<Note>
A real system would never put arguments and results in its telemetry. losim does
deliberately: the point is to watch a computation happen, and nodes exchanging
opaque byte counts teach nothing.
</Note>

## Give the system something to look at

A last one that is about the simulation rather than the code. A system of four
identical nodes in one zone draws as four identical boxes.

```yaml
workers:
  count: 4
  prefix: w
  instance: c5.large
  zone: [eu-central-1a, eu-central-1b]
  runs: { Thumbnailer: src/lab/Shrinker.java }
  overrides:
    w3: { instance: a1.medium }
    w1:
      failures:
        - { kill: true, at: 900 refMs }
```

Two zones become two bands. An `a1.medium` among three `c5.large`s is visibly a
smaller box. And the kill is a red marker on the bar you can jump straight to with
`]`.
